# 用户反馈洞察 Skill

一个面向 Codex 的中文用户反馈分析工具，用于把访谈记录、客服工单、问卷开放题和应用商店评论，转成**可回到原始证据的产品问题、矛盾与验证机会**。

它不会把“用户想要某个功能”直接当成需求，也不会把几条反馈包装成整体用户结论。Skill 先建立证据台账，识别重复、独立来源、样本偏差和相反意见，再分别判断问题的严重度、证据置信度与战略匹配，最后给出下一步行动。

## 🎯 它解决什么问题

用户反馈天然是嘈杂的：

- 同一个问题可能被同一用户重复提交，也可能被多个系统重复收录；
- 应用商店差评页、客服工单和主动访谈都有明显的样本选择偏差；
- 用户经常表达具体方案，但方案背后的任务与问题未必清楚；
- 高频问题不一定严重，单条安全或数据丢失反馈也不能因低频被忽略；
- 相反意见可能来自不同用户分群，而不是简单互相抵消；
- AI 很容易快速总结并生成路线图，却让结论失去证据来源。

常见的反馈分析工具偏向词频、情感和标签统计。这些结果可以描述材料，却不一定能回答产品决策真正关心的问题：

> 这是什么用户、在什么场景、遇到了什么问题？证据有多强？它与当前产品方向是否匹配？现在应该修、验证、观察，还是不推进？

这个 Skill 将反馈整理设计成一条证据链：

**原始记录 → 证据原子 → 主题与矛盾 → 产品机会 → 最小验证动作**

每个机会都保留相关证据 ID、反证、样本内频次、独立来源和最大未知，让后续讨论能够回到材料，而不是依赖一段流畅但不可复核的总结。

## 🧭 洞察模型

### 1. 先控制证据，再提炼主题

每条反馈都会被拆成场景、问题、影响、替代方式、用户方案和不确定性。重复记录不会被直接删除，而是保留并标记 `duplicate_of`，避免丢失审计线索。

记录数和独立来源数分别表达：

- **记录数**：材料中出现多少次；
- **独立来源**：有多少不同用户、账号、事件或渠道支持。

同一用户连续三次报告同一问题，说明问题可能持续或可复现，但独立来源仍是 1。这个区别能防止重复反馈制造虚假多数。

### 2. 保留矛盾，而不是只做多数投票

Skill 按用户任务和问题聚类，不按功能名分类。相反反馈、异常样本和无法解释项会和共性主题一起保留。

例如，一名用户希望账单默认展示全年，另一名用户希望保持按月。当前证据首先支持的不是任意一个默认值，而是“默认时间范围依赖使用场景”。后续可以验证是否需要记住上次选择，而不是仓促修改全局行为。

### 3. 把五个判断维度分开

| 维度 | 解决的问题 |
| --- | --- |
| **样本内频次** | 当前材料中出现了多少次，去重前后如何变化 |
| **独立来源** | 有多少不同用户、账号、事件或渠道支持 |
| **严重度** | 是否阻断核心任务、造成损失或只是体验偏好 |
| **证据置信度** | 场景、环境、复现信息、日志与反证是否充分 |
| **战略匹配** | 是否服务当前目标用户、核心价值和产品阶段 |

这些维度不会被压缩成一个看似精确的分数。高严重度、低置信度的问题通常需要快速调查；高频但低战略匹配的诉求，也不应自动进入当前路线图。

### 4. 先写机会，再讨论功能

产品机会使用统一结构：

> [目标用户] 在 [具体场景] 因 [问题] 无法或难以 [任务]，造成 [影响]。

每个机会都附带证据、反证、样本边界和最小验证动作。用户提出的功能只是候选响应，不等于已经证明应该开发。

### 5. 用行动建议表达产品取舍

| 行动建议 | 适用情况 |
| --- | --- |
| **立即处理** | 已确认的高严重度故障、安全、合规或不可逆风险 |
| **进入验证** | 问题值得继续，但覆盖面、根因或方案仍不确定 |
| **持续观察** | 信号存在，但独立来源、影响或战略依据不足 |
| **暂不推进** | 与目标用户或当前阶段不匹配，或反证已经明确 |

每个建议必须说明理由、依据和会改变判断的下一步，不以“继续调研”作为空泛结论。

## 🛠️ 使用方法

按照 [OpenAI 当前 Skills 指南](https://developers.openai.com/codex/skills/)，将完整目录安装到用户级 Skills 目录：

```bash
git clone https://github.com/jiaxuan-tao/vibe-coding-lab.git
mkdir -p "$HOME/.agents/skills/user-feedback-insight"
cp -R vibe-coding-lab/user-feedback-insight-skill/. \
  "$HOME/.agents/skills/user-feedback-insight/"
```

请复制完整目录，因为 `SKILL.md` 会按输入情况调用只读脚本或读取详细判断框架。安装后重新打开 Codex 任务，让 Skill 被发现。

**当前 Codex 构建的兼容路径**：部分仍使用旧版发现机制的构建会扫描 `$CODEX_HOME/skills`；未设置 `CODEX_HOME` 时通常对应 `$HOME/.codex/skills`。只有确认当前构建未发现 `.agents/skills` 中的 Skill 时，才将完整目录复制到 `$CODEX_HOME/skills/user-feedback-insight`。这是兼容方案，不是跨版本通用的首选安装位置。

安装后，可以在 Codex 中提出：

- `分析这批访谈记录，找出有证据支持的产品机会`
- `整理这些客服工单，区分重复问题、独立用户和高严重度异常`
- `分析这份应用商店评论 CSV，但不要把差评页比例外推到全部用户`
- `比较这些相反反馈，告诉我应该修复、验证、观察还是暂不推进`
- `先提炼机会，再把已确认机会整理成路线图候选`

默认只做反馈洞察，不直接编写 PRD 或修改用户文件。只有用户明确要求时，才会把已确认机会继续整理成需求输入。

### 本地反馈预处理

当输入是本地 UTF-8 Markdown、TXT、CSV 或 JSON 时，可以先生成统一证据记录：

```bash
cd vibe-coding-lab/user-feedback-insight-skill
python3 scripts/prepare_feedback.py /path/to/feedback.csv
```

CSV 支持常见反馈列名，例如 `feedback`、`text`、`comment`、`review`、`反馈`、`评论`；如果存在 `user_id`、`source`、`用户`、`渠道` 等来源字段，脚本会同时统计独立来源。

输出示意：

```json
{
  "summary": {
    "record_count": 4,
    "unique_record_count": 3,
    "duplicate_count": 1,
    "unique_source_count": 3,
    "pii_record_count": 0
  },
  "warnings": [
    "检测到 1 条可能重复记录；重复不应增加独立证据强度。"
  ],
  "records": [
    {
      "id": "FB-0001",
      "source_line": 2,
      "source": "U-101",
      "text": "更新后无法打开，急用。",
      "duplicate_of": null,
      "pii_types": []
    }
  ]
}
```

脚本只处理可机械验证的结构：格式、稳定 ID、可能重复、来源和潜在直接身份信息。它不会自动判断主题、情感、机会或优先级。

## 🧾 输出示例

```text
用户反馈洞察 · 2026-07-30

分析范围与限制
- 输入共 6 条客服记录，去重后 5 条。
- 已知独立来源 4 个；其中一条缺少来源，独立来源数可能被低估。
- 样本来自新版本上线后一周的主动工单，只能发现问题线索，不能代表全部用户。
- 两条记录含直接身份信息，分析中已只使用匿名证据 ID。

证据台账
- FB-0001｜U-204｜筛选日期后返回，筛选条件偶尔被重置。
- FB-0002｜U-204｜三天后再次反馈同一现象；这是持续性证据，不增加独立来源。
- FB-0003｜匿名来源｜账单页加载超过十秒，但用户同时说明网络不稳定。
- FB-0004｜U-301｜希望默认展示全年账单。
- FB-0005｜U-118｜认为全年太乱，希望保持按月。

主题与矛盾
1. 日期筛选状态丢失
   - 相关证据：FB-0001、FB-0002
   - 样本内频次：2/5；独立来源：1
   - 影响：用户返回后需重新设置查询条件。
   - 缺口：版本、设备、复现路径缺失。

2. 默认时间范围
   - 相关证据：FB-0004、FB-0005
   - 样本内频次：2/5；独立来源：2
   - 矛盾：全年与按月偏好直接相反，可能对应不同使用任务。

产品机会
机会 A：频繁查询账单的用户在详情返回场景中可能丢失筛选上下文，
需要重复设置条件，增加查询成本。
- 相关证据 ID：FB-0001、FB-0002
- 反证：暂无独立用户佐证，且问题被描述为“偶尔”
- 严重度：中
- 证据置信度：中低
- 战略匹配：高
- 最小验证动作：补版本、设备和返回路径，在当前版本完成 3 条路径复现。

行动建议
- 机会 A：进入验证。影响具体且同一用户重复遇到，但独立来源只有 1，
  先复现并检查状态恢复逻辑，不直接承诺完整改造。
- 默认时间范围：持续观察。意见相反且各只有一个来源，先分析月度与年度筛选行为。
- 加载慢：持续观察并补性能数据；单条弱网反馈不足以建立性能缺陷。

待补证据
1. 日期筛选问题的版本、设备、返回路径和复现率。
2. 月度/年度筛选的真实使用分布与任务差异。
3. 正常网络和弱网下的账单接口、首屏渲染耗时。
```

这份输出不是功能清单，而是一张可复核的机会地图：哪些问题已经足够明确，哪些只值得验证，哪些证据仍不能支持投入，都能回到具体记录。

## ✨ 核心能力

- 建立稳定证据 ID，让主题、机会和行动建议能够回到原始材料。
- 区分记录次数与独立来源，防止同一用户、同一事件或跨系统重复被计算为多人验证。
- 显式标记抽样偏差，只描述样本内频次，不制造总体用户比例。
- 将复合反馈拆成场景、问题、影响、替代方式、用户方案和不确定性。
- 保留相反意见、反证、高严重度异常和无法归类项，不只输出多数主题。
- 分开判断严重度、证据置信度与战略匹配，避免单一优先级掩盖判断依据。
- 先定义产品机会，再讨论候选响应，阻止“用户要功能 → 直接立项”的跳跃。
- 用立即处理、进入验证、持续观察和暂不推进表达不同决策动作。
- 对潜在手机号和邮箱提供隐私提醒，同时保持本地文件只读。

## 🧪 本地验证

项目只使用 Python 标准库。运行全部自动测试：

```bash
cd vibe-coding-lab/user-feedback-insight-skill
python3 -m unittest discover -s tests -p 'test_*.py' -v
```

自动测试覆盖：

- Markdown、TXT、CSV 和 JSON 输入；
- 稳定 ID、行号、来源和重复关系；
- 邮箱与中国大陆手机号形式提醒；
- 文件不存在、目录、非 UTF-8、空内容和无反馈列等错误；
- 输入文件只读；
- Skill frontmatter、输出契约、安装说明、本地链接和许可证；
- 仓库索引与展示页边界。

行为验证记录保存在 [`tests/baseline-evaluation.md`](tests/baseline-evaluation.md)、[`tests/trigger-evaluation.md`](tests/trigger-evaluation.md) 和 [`tests/forward-evaluation.md`](tests/forward-evaluation.md)。文档化评估保存真实提示词、输出和改进矩阵，不伪装成自动化测试。

## ⚠️ 能力边界

- 它是反馈证据整理与产品机会判断工具，不替代正式用户研究、统计抽样、数据分析或业务评审。
- 文本重复只能提示“可能重复”，无法自动确认是否来自同一用户或同一事件。
- 来源字段缺失时不能准确计算独立用户数；Skill 会保留缺口，而不是估算。
- 当前样本中的比例不能代表总体发生率，尤其不能外推差评页、客服工单或主动访谈。
- PII 检测只覆盖有限的邮箱和中国大陆手机号形式，不是完整匿名化或合规工具。
- 用户原话中的功能请求仍需还原任务和问题，不会自动成为需求或路线图承诺。
- 严重度高只表示需要重视，不代表根因、覆盖面或具体方案已经确认。
- 默认不修改用户文件，也不自动创建 PRD、Issue 或外部任务。

## 🤖 AI 辅助开发说明

本项目通过 Vibe Coding 方式迭代。作者负责定义产品问题、证据台账、独立来源规则、样本边界、矛盾处理、机会结构、决策动作和最终验收标准；Codex 用于协助实现 Skill、只读预处理脚本、自动测试和文档整理。

项目的产品价值不来自让 AI 更快地产生总结，而来自主动约束 AI 的判断路径：证据没有独立来源就不能称为多人验证，偏差样本不能外推总体，用户方案不能直接等同需求，结论必须带着反证和下一步动作。这些约束让反馈分析能够进入后续产品决策，而不只是生成一份阅读体验良好的报告。
