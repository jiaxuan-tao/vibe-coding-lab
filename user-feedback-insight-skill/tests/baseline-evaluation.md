# 无 Skill 基线评估

评估日期：2026-07-30

本文件记录三个独立代理在**未读取本 Skill 和仓库文件**时的原始表现。所有姓名、账号、手机号、邮箱和反馈内容均为测试构造，不是真实用户数据。

## 场景 A：访谈反馈直接转功能优先级

### Prompt

```text
请分析下面 6 条访谈反馈，告诉我最值得做的功能以及优先级。
1. 独立开发者 A：每次导入 CSV 后字段名称不一样，我要重新对应列，很费时间。
2. 独立开发者 B：最痛苦的是不知道导入失败在哪一行，通常只能整份重来。
3. 运营 C：希望系统自动帮我修正所有错误，不想看复杂提示。
4. 独立开发者 D：字段映射我只配置过第一次，后面一直沿用，没觉得麻烦。
5. 运营 E：上传失败时，我更想先下载错误行，改完再补传。
6. 企业管理员 F：我们需要 SSO 和五级权限，否则无法采购。
```

### Verbatim output

```markdown
最值得做的是：**导入失败后的“错误定位—导出—修复—补传”闭环**，优先级 P0。

原因是 B 和 E 的反馈相互印证：问题不只是“上传失败”，而是失败后不知道哪里错、只能整份重来，恢复成本很高。这个功能应包含：

- 明确标出失败行、字段和错误原因
- 一键下载错误行
- 用户修复后仅补传错误数据
- 保留已成功导入的记录，避免整份回滚

### 建议优先级

| 优先级 | 功能 | 判断依据 |
|---|---|---|
| P0 | 行级错误定位、错误行下载、修复后补传 | B、E共同验证，痛点强且场景具体，能显著降低失败后的返工成本 |
| P1 | 字段映射模板与智能匹配 | A有明显痛点，但D说明映射一旦能复用，问题可能并不普遍。建议支持保存映射模板、识别历史表头及字段别名，而不是重做整个映射流程 |
| P2 | 安全范围内的自动纠错 | C表达了需求，但“自动修正所有错误”风险较高，可能造成静默数据污染。可先自动处理日期格式、空格、大小写等低风险错误，高风险修改必须预览或确认 |
| 条件性 P0 / 否则暂缓 | SSO与五级权限 | 对企业客户是采购门槛，不是普通体验优化。若当前明确进军企业市场或已有真实商机，应作为企业版本P0；若主要用户仍是独立开发者和运营，不应仅凭一条反馈挤占导入体验的资源 |

### 推荐实施顺序

1. 先完成失败恢复闭环：定位错误行 → 下载 → 修复 → 补传。
2. 再减少导入前的重复操作：保存映射模板、表头别名匹配、匹配结果预览。
3. 收集常见错误类型后，仅对可逆、低风险问题提供自动修复。
4. 单独验证企业采购机会，再决定是否投入 SSO 和五级权限。

核心判断是：**先让用户在导入失败后能够低成本恢复，再减少失败发生，最后才考虑替用户自动改数据。** SSO和权限体系应由企业市场策略决定，不能与通用导入体验放在同一条优先级队列里。
```

### 基线缺口

- 直接从问题进入功能优先级，没有先形成产品机会。
- 没有统一证据台账，结论依赖原始序号和人物代号。
- 未说明六条访谈的招募方式、用户结构和样本边界。
- 将 B、E 称为“共同验证”，但没有定义独立来源与证据置信度。

## 场景 B：重复评论与偏差样本

### Prompt

```text
这些是应用商店抓取到的 8 条评论，请总结用户痛点、估算各问题占比，并给出路线图。
1. 同步经常失败，已经第三次了。
2. 同步经常失败，已经第三次了。
3. 新版界面很好看。
4. 更新后打不开，急用。
5. 更新后打不开，急用。
6. 希望增加深色模式。
7. 客服让我重装后可以打开了。
8. 不支持导出 PDF，很遗憾。
说明：抓取脚本可能重复收录评论，且这里只是最新差评页的部分样本。
```

### Verbatim output

```markdown
结论：当前最需要优先处理的不是功能新增，而是“更新后无法打开”和“同步失败”两项可靠性问题。但样本很小、来自最新差评页且含重复评论，比例只能代表本页，不能外推到全部用户。

### 数据清洗与问题占比

8 条原始评论中有两组完全重复：

- #1 = #2
- #4 = #5

因此精确去重后为 6 条，重复率为 25%。#7 可能与“更新后打不开”来自同一事件，也可能是独立用户，证据不足，不应直接合并。

| 问题 | 原始样本占比 | 去重后占比 | 判断 |
|---|---:|---:|---|
| 更新后无法打开/需重装恢复 | 3/8，37.5% | 2/6，33.3% | 最高优先级；阻断使用，且与版本更新直接相关 |
| 同步经常失败 | 2/8，25.0% | 1/6，16.7% | 高频复发描述明确，“第三次”说明不是偶发现象 |
| 缺少深色模式 | 1/8，12.5% | 1/6，16.7% | 体验型需求，不阻断核心任务 |
| 不支持导出 PDF | 1/8，12.5% | 1/6，16.7% | 功能缺口，可能阻断分享、归档或交付流程 |
| 新版界面好看 | 1/8，12.5% | 1/6，16.7% | 正向反馈，不属于痛点 |

若只统计去重后的 5 条“问题相关评论”，启动问题约占 40%，其他三类各占 20%。这些数字仍不能视为产品整体问题率。

### 用户痛点总结

1. **版本更新破坏可用性**  
   更新后无法启动，用户还处于“急用”场景，影响最严重。重装虽然有效，但可能带来数据丢失顾虑，也不是合格的长期解决方案。

2. **同步可靠性不足且反复发生**  
   用户明确表示已发生三次，说明问题可能涉及重试、网络异常处理、状态一致性或同步任务恢复机制。

3. **关键输出能力缺失**  
   缺少 PDF 导出会影响保存、打印、分享和跨平台交付，实际业务影响可能高于评论数量所显示的程度。

4. **显示体验不完整**  
   深色模式属于明确但非紧急的体验诉求，应排在可靠性修复之后。

### 建议路线图

**P0｜立即止损（1–3 天）**

- 排查更新后启动失败：升级迁移、缓存、数据库版本、权限及初始化流程。
- 补充启动失败和同步失败的错误日志、版本号、设备及失败阶段信息。
- 在客服和帮助中心提供安全恢复流程，明确重装前的数据备份与同步状态。
- 检查是否需要暂停问题版本的继续发布或灰度扩量。

**P1｜可靠性修复（1–2 周）**

- 修复启动回归，并增加“旧版本升级到新版本”的自动化测试。
- 为数据迁移增加失败回滚或自修复机制，避免只能依赖重装。
- 改进同步：自动重试、指数退避、断点恢复、幂等处理和明确的失败提示。
- 向用户展示同步状态及“重新同步”入口，避免静默失败。

验收指标建议包括：升级后启动成功率、无崩溃会话率、同步成功率、重试恢复率，以及相关客服工单量。

**P2｜功能补齐（2–4 周）**

- 优先验证 PDF 导出的真实使用场景、格式要求和内容范围，推出最小可用版本。
- 开展深色模式适配，同时检查颜色对比度、图片、图表及系统主题跟随。

**P3｜持续验证**

- 对抓取数据做评论 ID、用户 ID、时间和文本指纹去重。
- 扩大到多个版本、评分区间和时间窗口，避免只分析最新差评页。
- 将商店评论与崩溃日志、同步失败率、客服工单交叉验证，再决定中长期投入比例。
```

### 基线缺口

- 已正确识别重复与样本偏差，但仍按记录分母给出多组精确百分比，容易让读者忽略样本选择偏差。
- 把单一独立评论中的“第三次”描述为高频复发，混合了同一用户的事件频率与用户覆盖面。
- 从主题直接进入路线图，没有独立的机会陈述、反证与最小验证动作。

## 场景 C：同一用户重复、矛盾反馈与直接身份信息

### Prompt

```text
请把下面客服记录整理成需求，尽量给出明确结论。
- 2026-07-12，王女士（手机号 13800000000）：账单页加载慢，等了十几秒；但她说最近网络也不稳定。
- 2026-07-13，用户 U-204：账单页很快，不过筛选日期后偶尔丢失筛选条件。
- 2026-07-14，李先生（li@example.com）：希望默认展示全年账单。
- 2026-07-15，用户 U-118：默认全年会太乱，希望保持按月。
- 2026-07-16，用户 U-204：再次反馈筛选返回后被重置。
- 内部客服备注：本周新版本刚上线，但没有提供版本号或设备信息。
```

### Verbatim output

```markdown
## 客服记录需求整理

### 明确结论

1. **优先修复“日期筛选条件被重置”问题。**  
   同一用户在 7 月 13 日和 7 月 16 日重复反馈，现象一致，说明并非一次性误操作。建议按缺陷处理，优先级定为 **P1（高）**。

2. **暂不调整账单页的全局默认时间范围。**  
   “默认全年”和“保持按月”是直接冲突的个体偏好，目前各只有一条反馈，证据不足以支持全局改版。现阶段应保持按月默认；如后续需求量明确，可考虑记住用户上次选择或提供个人默认设置。

3. **“账单页加载慢”暂不能确认是产品性能问题。**  
   目前只有一例，且用户同时说明网络不稳定。应先补充性能数据和环境信息，不建议仅凭该记录立即立项优化。

4. **无法判断问题是否与本周新版本有关。**  
   客服记录缺少版本号、设备、操作系统、网络类型和发生时间等信息，不能建立版本上线与问题之间的因果关系。

---

### 需求一：保留日期筛选状态

- **类型：** 缺陷修复
- **用户场景：** 用户在账单页设置日期筛选条件，进入账单详情或其他页面后再返回。
- **现存问题：** 返回账单页后，原筛选条件偶尔被清空或恢复默认值。
- **需求结论：** 在用户主动清除、修改筛选条件或结束当前业务流程前，账单页应保留已选日期范围。
- **建议验收标准：**
  - 设置日期筛选后进入详情页，再返回，筛选条件和结果保持不变。
  - 前后台切换、页面刷新及常见返回方式下，行为符合产品定义。
  - 用户主动点击“重置”后，才恢复默认日期范围。
  - 补测新版本升级前后的状态兼容性。
- **优先级：** P1
- **证据强度：** 较高；同一用户两次反馈相同现象。
- **待确认：** “偶尔”出现的具体触发路径、客户端版本、设备及操作系统。

### 需求二：评估账单页加载性能

- **类型：** 性能调查，尚不能直接认定为缺陷
- **用户场景：** 用户打开账单页。
- **反馈现象：** 单次加载超过十秒。
- **影响判断：** 若在正常网络下普遍发生，会显著影响账单查询体验；但当前证据不足。
- **建议处理：**
  - 采集账单接口耗时、首屏渲染耗时、失败率及网络类型。
  - 分别在稳定 Wi-Fi、移动网络和弱网环境复测。
  - 若正常网络下仍超过既定性能标准，再建立优化需求。
- **建议性能目标：** 具体阈值需结合现有基线确定，不宜直接把单个用户的“十几秒”作为产品标准。
- **优先级：** P2 调查
- **证据强度：** 低；仅一例且存在网络干扰因素。

### 需求三：账单默认时间范围

- **类型：** 产品体验需求
- **冲突反馈：**
  - 一名用户希望默认展示全年账单。
  - 一名用户认为全年信息过多，希望继续按月展示。
- **需求结论：** 暂时保留“默认按月”，不做全局切换。
- **后续方案优先顺序：**
  1. 保留按月默认，同时让“全年”入口清晰易用。
  2. 记住用户上一次选择的时间范围。
  3. 只有在数据证明多数用户长期需要全年视图时，再考虑修改全局默认值。
- **优先级：** P3
- **证据强度：** 低；样本少且意见相反。
- **需要补充的数据：** 月度/年度筛选使用占比、切换频率、查询任务完成率，以及更大规模的用户反馈。

### 客服记录改进要求

后续涉及页面异常或新版本问题时，客服至少应记录：

- 用户匿名 ID，避免在需求单中保留手机号、邮箱等直接身份信息
- App 或网页版本号
- 设备型号及操作系统版本
- 网络类型和网络状态
- 问题发生时间
- 完整操作路径
- 出现频率及是否可以复现
- 截图、录屏或错误提示
- 是否在升级新版本后首次出现

本批记录中，手机号和邮箱不应继续进入产品需求或缺陷跟踪系统，使用匿名用户标识即可。
```

### 基线缺口

- 已识别隐私、矛盾和因果证据不足。
- 将同一用户两次反馈评价为“证据强度较高”，没有把持续性与独立来源多样性拆开。
- 直接整理成三个需求，弱化了“筛选状态丢失”是问题机会，而“保留状态”只是候选响应。
- 没有稳定证据 ID，后续需求、反证和验证动作无法机械回链。

## 失败矩阵

| 基线失败 | A | B | C | Skill 应有行为 |
| --- | --- | --- | --- | --- |
| 缺少稳定证据 ID | 是 | 是 | 是 | 建立证据台账并让结论引用 ID |
| 同一来源被当作独立佐证 | 风险 | 是 | 是 | 分开记录次数与独立来源 |
| 样本比例可能被过度解释 | 风险 | 是 | 风险 | 只陈述样本内频次并写清偏差 |
| 直接从反馈进入功能或需求 | 是 | 是 | 是 | 先形成问题机会，再讨论方案 |
| 矛盾或异常被隐藏 | 否 | 否 | 否 | 继续保留矛盾、反证与异常 |
| PII 未提醒 | 不适用 | 不适用 | 否 | 继续提示并避免复述原值 |

基线已经具备较好的常识判断，因此 Skill 不需要重复通用产品分析知识。它需要用稳定结构把“知道应该谨慎”变成每次分析都能检查的证据契约。
