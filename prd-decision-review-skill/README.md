# PRD 需求决策评审 Skill

一个面向 Codex 的中文需求评审工具，用于回答产品设计或开发开始前最重要的问题：**这个需求现在值得推进吗？如果还不值得，最小需要补什么？**

它不按章节数量评价 PRD，也不替用户补出看似完整的答案。它先区分证据、假设与待确认事项，再检查用户问题、目标、MVP、流程、成功指标和验收是否形成闭环，最后给出可进入设计、有条件进入或暂不建议推进的唯一 Gate 结论。

## 🎯 它解决什么问题

AI 很容易把一句产品想法扩写成结构完整的 PRD，但“写得完整”和“值得开发”不是一回事。真正影响推进决策的通常是：

- 目标用户和具体场景是否成立，还是先有方案再倒推问题；
- 用户反馈、行为数据与产品人员的推断是否被混在一起；
- MVP 是否形成最小价值闭环，还是把后续能力一起塞进首版；
- 成功指标能否验证目标，而不只是“提升体验”或“增加活跃”；
- 主路径、错误状态与外部依赖是否有用户可见的结果；
- 每项需求能否被验收，完成后是否知道它真的有效。

常见模板能提醒“应该写哪些章节”，却无法判断这些章节是否互相支持。这个 Skill 将 PRD 写作改造成一条需求决策链：从问题证据出发，收敛最小范围，用可观察指标与验收约束结果，再决定是否进入下一阶段。

## 🧭 决策模型

评审严格按前置决策到交付验证的顺序进行：

1. **用户问题**：谁在什么场景遇到什么障碍，现有做法为何不足。
2. **证据与假设**：区分材料中已确认的事实、合理但未验证的假设和待确认事项。
3. **目标与指标**：检查预期行为变化、指标口径、基线、目标值和观察周期。
4. **MVP 范围**：保留验证核心假设所需的最小闭环，同时写清包含项、排除项与后续项。
5. **关键流程**：覆盖触发、核心操作、用户可见结果、异常状态和中断后的去向。
6. **需求与验收**：让每项要求对应单一可观察行为，并用 GIVEN / WHEN / THEN 场景验证。
7. **依赖与风险**：说明外部服务、数据、权限、隐私、合规和不可逆动作的影响。
8. **一致性**：核对问题、目标、范围、流程、指标与验收是否互相支持。

Skill 不输出总分。它把关键发现分为阻塞项、需确认和可优化，并只给出以下一种结论：

| Gate 结论 | 含义 | 下一步 |
| --- | --- | --- |
| **可进入设计** | 问题、目标、核心范围和关键流程明确，主要需求可验证 | 进入交互与技术设计，继续跟踪非阻塞项 |
| **有条件进入** | 核心方向基本成立，但仍有影响范围、指标或流程的假设 | 只做有限原型或探索，先完成最小确认动作 |
| **暂不建议推进** | 问题依据、成功条件、范围基础或关键依赖尚不成立 | 停止细化方案，先验证问题或缩小范围 |

结论必须同时说明影响、依据与最小动作，避免把“再调研一下”当作可执行建议。

## 🧭 使用方法

按照 [OpenAI 当前 Skills 指南](https://developers.openai.com/codex/skills/)，将完整目录安装到用户级 Skills 目录：

```bash
git clone https://github.com/jiaxuan-tao/vibe-coding-lab.git
mkdir -p "$HOME/.agents/skills/prd-decision-review"
cp -R vibe-coding-lab/prd-decision-review-skill/. \
  "$HOME/.agents/skills/prd-decision-review/"
```

请复制完整目录，因为 `SKILL.md` 会按输入情况读取评审参考或调用只读检查脚本。安装后重新打开 Codex 任务，让 Skill 被发现。

**当前 Codex 构建的兼容路径**：部分仍使用旧版发现机制的构建会扫描 `$CODEX_HOME/skills`；未设置 `CODEX_HOME` 时通常对应 `$HOME/.codex/skills`。只有确认当前构建未发现 `.agents/skills` 中的 Skill 时，才将完整目录复制到 `$CODEX_HOME/skills/prd-decision-review`。这是针对特定构建的兼容方案，不是跨版本通用的首选安装位置。

安装后，在 Codex 中提出：

- `评审这份 PRD 是否可以进入设计，并指出最小补充动作`
- `检查这个需求的用户问题、MVP 范围和成功指标`
- `把这个模糊想法整理成可评审 Brief，不要虚构用户证据`
- `先评审，再按结论修订这份 PRD`

默认行为是评审，不会直接改写原文。只有明确要求修订时，Skill 才会在评审结论之后提供修订版，并继续标明假设和待确认项。

如果输入是本地 UTF-8 文本 PRD，可先运行零依赖结构检查；推荐使用 Markdown，方便人和 Codex 同时阅读：

```bash
cd vibe-coding-lab/prd-decision-review-skill
python3 scripts/inspect_prd.py /path/to/product-requirements.md
python3 scripts/inspect_prd.py /path/to/product-requirements.md --json
```

脚本逐行扫描全文中的预定义关键词信号、占位词、模糊表述和按顺序出现的 GIVEN / WHEN / THEN 场景。它不解析 Markdown 标题或真正的章节边界：正文、示例或注释里的同名词也可能命中，因此可能误报。输出只适合作为人工评审的线索，必须结合原文人工解读；脚本不修改源文件，也不自动给出质量分或 Gate 结论。

## 🧾 输出示例

```text
PRD 需求决策评审 · 2026-07-29

结论：有条件进入
一句话理由：目标用户和核心任务已明确，但成功指标缺少口径，
且企业权限能力超出当前个人使用场景，尚不能直接进入完整设计。

需求判断
- 目标用户与问题：独立开发者在访谈后手工整理待办，容易遗漏负责人和截止时间。
- 产品目标：让用户从访谈文本中确认并导出可执行待办。
- MVP 核心价值：粘贴文本 → 生成带来源的待办 → 人工确认 → 导出。

证据与假设
- 已确认：现有材料记录了 5 次手工整理及 2 次遗漏。
- 假设：带来源片段会提高用户对生成结果的信任。
- 待确认：当前整理耗时基线、用户可接受的修正成本。

关键发现
- [需确认] 成功指标只有“提升效率”，没有口径和目标值。
  影响：上线后无法判断 MVP 是否改善核心问题。
  依据：成功指标章节未定义分母、基线、目标值和观察周期。
  最小动作：记录 5 次现有流程耗时，并定义首次处理后确认待办比例。
- [阻塞项] 企业 SSO 和五级权限与已知个人场景不一致。
  影响：扩大设计与验证范围，却不帮助验证核心假设。
  依据：材料只提供个人使用场景，没有组织协作证据。
  最小动作：从 MVP 排除企业权限；若坚持纳入，先补充目标组织与授权需求。

范围与关键流程
- 本次包含：粘贴文本、生成待办、来源回看、人工确认、导出。
- 明确排除：音视频转写、团队权限、跨组织 SSO、自动发送任务。
- 核心路径：提交文本 → 查看生成结果 → 核对来源 → 修改或确认 → 导出。

进入下一阶段前
1. 定义主指标的基线、目标值和两周观察周期。
2. 将企业能力移出 MVP，并补充生成失败与低置信度状态的验收场景。
```

输出不是一份被 AI 补齐的新 PRD，而是一张可追溯的推进决策单：每个结论都能回到输入证据，每个缺口都有影响和最小动作。

## ✨ 核心能力

- 把“写一份 PRD”重新定义为“判断需求是否值得进入下一阶段”。
- 在评审开头区分已确认、假设和待确认，避免 AI 推测污染产品事实。
- 先判断用户问题与方案方向，再检查章节细节，及时阻止 solution-first。
- 用核心假设切分 MVP，并通过明确排除项控制范围扩张。
- 建立“用户问题 → 目标行为 → 成功指标 → 验收场景”的可追溯链路。
- 检查主路径、错误状态、依赖、隐私、权限和不可逆动作的用户可见结果。
- 用单一 Gate、影响、依据和最小动作表达产品取舍，不制造虚假精确的总分。
- 对模糊想法先输出轻量 Brief；仅在用户明确要求时修订完整 PRD。

## 🧪 本地验证

项目只使用 Python 标准库。运行全部自动测试：

```bash
cd vibe-coding-lab/prd-decision-review-skill
python3 -m unittest discover -s tests -p 'test_*.py' -v
```

检查器接受 UTF-8 文本文件，不限制扩展名，推荐使用 Markdown。它默认输出可读文本，使用 `--json` 可获得机器可读结果；文件不存在、目录输入或非 UTF-8 内容会返回退出码 2。

## 🛠️ 技术实现

- **评审流程**：`SKILL.md` 定义输入分类、八步评审顺序、三种 Gate 与按需修订边界。
- **判断口径**：`references/prd-review-framework.md` 提供强弱示例、常见失败模式和争议结论的校准规则。
- **文本信号**：`scripts/inspect_prd.py` 使用 Python 标准库扫描全文关键词、占位词、模糊措辞和验收场景序列；它不是 Markdown 章节解析器。
- **可执行测试**：`unittest` 覆盖检查脚本的输入与只读行为，以及 Skill 和文档的静态契约。
- **行为证据**：[`tests/forward-evaluation.md`](tests/forward-evaluation.md) 保存输出行为评估，[`tests/trigger-evaluation.md`](tests/trigger-evaluation.md) 保存 Skill 选择边界的真实执行尝试与外部发送阻塞；它们属于文档化的行为证据，不是可执行 `unittest`。
- **运行边界**：不依赖数据库、远程模型 API、上游 CLI 或额外 Python 包。

文本信号扫描与产品判断被刻意分开：关键词命中既不能证明某个章节存在，也不能证明内容质量；最终 Gate 仍需结合原文、证据强度、范围取舍和业务上下文。

## ⚠️ 能力边界

- 它是需求推进决策工具，不替代真实用户研究、数据分析、商业评估或正式评审会议。
- 关键词扫描可能因正文或示例命中而误报，只能提供材料线索，不能证明章节存在、用户问题真实或自动作出 Gate 决策。
- “可进入设计”表示当前证据足以进入下一阶段，不保证产品最终取得商业成功。
- 没有来源的数据、用户反馈和业务约束会保留为假设或待确认，不会被补写成事实。
- 它不生成技术架构、实施任务或代码，也不根据章节数量计算 PRD 质量分。
- 默认不修改用户文件；修订模式必须由用户明确触发。

## 🤖 AI 辅助开发说明

本项目通过 Vibe Coding 方式迭代。作者负责定义产品问题、评审顺序、证据分层、MVP 判断、成功指标与验收链路、Gate 规则、能力边界和最终验收标准；Codex 用于协助实现 Skill、只读检查脚本、自动测试和文档整理。

这里的产品判断不来自“让 AI 写得更完整”，而来自主动限制 AI：没有证据就保留为假设，范围无法闭环就停止扩写，成功无法观察就不能把需求当作已完成。最终推进决定仍由使用者结合真实业务上下文承担。
