~~~~markdown
# PRD｜AI 自动整理会议记录（MVP）

## 1. 输入分类与缺失材料

**已确认**

- 产品形态：AI 自动整理会议记录工具。
- 发起者：独立开发者。

**假设**

- 首批目标用户是经常参加线上会议、会后需要向团队同步结论的个人知识工作者与小型团队负责人。
- 用户可提供会议录音或录音转写文本；MVP 不负责会议实时录音。
- 用户最需要的是可核对的会议摘要、待办与决策，而不是逐字稿本身。

**待确认 / 缺失材料**

- 首发行业、语言、会议平台、目标市场与付费意愿。
- 用户当前如何整理会议记录、耗时多少、其中哪些环节最痛。
- 音频来源是否有合法授权，以及数据保存地区、保留期限和隐私要求。
- 可用的语音转写与大模型服务、预算、准确率和延迟约束。

## 2. 用户问题

### 目标用户（假设）

每周至少参加 3 场线上会议、需要在会后形成可执行同步内容的独立开发者、小团队负责人、产品/项目协作人员。

### 使用场景

用户结束一次会议后拿到音频或转写文本；现有逐字稿冗长且杂乱，需要手工找出结论、待办、负责人和截止时间，再粘贴到文档或项目工具中。

### 现有替代方案

- 手工记录或会后回听录音：信息可控，但耗时且易漏项。
- 会议平台自带转写/摘要：使用方便，但格式、语言、任务提取和导出能力可能不匹配。
- 通用大模型手工粘贴转写：灵活，但每次需要写提示词，原文与结论对应关系较弱。

需通过 5–8 名目标用户访谈确认上述问题是否高频且足以驱动持续使用。

## 3. 产品目标与非目标

### 目标

让用户在上传会议材料后，快速得到一份可核对、可编辑、可分享的结构化会议纪要，减少会后整理时间。

### 非目标（MVP 不做）

- 不做会议机器人入会、实时字幕或实时建议。
- 不做多人协同编辑、组织级权限、知识库问答与复杂项目管理。
- 不承诺替代人工确认；AI 输出不能自动执行外部任务。
- 不支持无授权的录音采集或未告知参会者的数据处理。

## 4. 成功指标与口径

| 指标 | MVP 目标 | 口径 | 当前状态 |
| --- | --- | --- | --- |
| 首次价值达成率 | ≥60% | 新用户在首次上传后成功打开生成纪要 | 假设，待基线验证 |
| 纪要生成完成率 | ≥90% | 已开始处理的材料中，24 小时内成功生成纪要的比例 | 假设，待确认 |
| 核心摘要可直接使用率 | ≥70% | 用户不修改或仅轻微修改后导出/复制纪要的比例；需定义“轻微修改” | 待确认 |
| 会后整理时间 | 较手工方式减少 50% | 用户自报的从会议结束到可发送纪要的耗时对比 | 假设，需访谈验证 |
| 隐私事件 | 0 起 | 已确认的未授权访问、错误共享或超出保留规则的数据事件 | 目标 |

## 5. MVP 范围

### 最小闭环

上传或粘贴会议材料 → 选择纪要语言/模板 → AI 生成结构化纪要 → 用户核对编辑 → 复制或导出。

### 纳入

- 登录或一次性访问机制，用于区分用户数据。
- 粘贴转写文本；上传常见音频文件作为可选入口。
- 单一默认模板：会议概览、摘要、决策、行动项、待确认问题。
- 行动项字段：事项、负责人、截止时间、来源片段（若原文可定位）。
- 编辑、复制 Markdown/纯文本、下载 Markdown。
- 数据删除入口和明确的保存期限说明。

### 排除

- Zoom/Google Meet/Teams 自动同步。
- 自定义模板、团队空间、第三方项目管理工具双向同步。
- 多语言混说的高准确率承诺、声纹级说话人识别。
- 会议质量评分、销售辅导、跨会议知识沉淀。

## 6. 关键流程

1. 用户进入工作台，看到数据处理说明和上传/粘贴入口。
2. 用户粘贴转写文本，或上传音频并确认其有权处理该录音。
3. 用户选择输出语言与默认模板，提交处理。
4. 系统显示处理状态；失败时给出可理解的原因与重试方式。
5. 系统返回结构化纪要；每个行动项可回看相关原文片段。
6. 用户修订内容后复制或下载，并可删除源材料与纪要。

**主要断点与应对**

- 音频长、质量差或转写失败：限制文件时长/格式，提示处理预估，保留重试和改用文本粘贴入口。
- AI 虚构负责人或日期：无法从原文确定时显示“待确认”，不得编造。
- 用户担忧机密信息：上传前说明用途、保存规则和删除方式；默认不将数据用于模型训练，前提是技术供应商条款允许。

## 7. 功能需求与验收标准

| 编号 | 需求 | 验收标准 |
| --- | --- | --- |
| FR-1 | 提供文本粘贴与音频上传入口 | 用户可提交符合格式和大小限制的材料；不符合时能看到具体限制和修正方式。 |
| FR-2 | 将音频转为可处理文本 | 对成功上传的音频，系统展示转写结果或明确失败状态；原始音频与转写归属同一会议记录。 |
| FR-3 | 生成结构化纪要 | 每份成功处理的记录均包含会议概览、摘要、决策、行动项、待确认问题五个区块；原文未出现的信息不得作为确定事实输出。 |
| FR-4 | 行动项可追溯 | 若原文存在对应内容，每条行动项可打开相关原文片段；无法定位时标注“来源待确认”。 |
| FR-5 | 用户可编辑与导出 | 用户可修改任一纪要字段，并能复制为 Markdown/纯文本或下载 Markdown 文件；导出内容与当前编辑内容一致。 |
| FR-6 | 数据控制 | 用户可删除单条会议数据；删除后该用户在正常产品入口无法再访问该记录。实际物理删除时限和备份规则待确认。 |
| FR-7 | 异常处理 | 转写或摘要失败时，系统不显示伪造结果，保留原材料状态并提供重试或联系支持的路径。 |

## 8. 依赖与风险

| 类别 | 风险 / 依赖 | 影响 | 最小应对动作 |
| --- | --- | --- |
| 技术 | 语音转写质量、长音频成本和处理时延 | 直接影响核心体验与毛利 | 用真实样本压测时长、成本、失败率；先设文件时长上限。 |
| 模型质量 | 摘要遗漏、幻觉、任务归属错误 | 用户不能信任结果 | 强制不确定性标注、原文回链、编辑后导出。 |
| 数据与合规 | 录音授权、个人信息、跨境处理、供应商留存 | 可能造成合规与声誉风险 | 处理前取得确认；确定隐私政策、数据流向、保留和删除机制后再开放上传。 |
| 市场 | 会议平台和通用 AI 已提供类似摘要 | 获客和留存困难 | 访谈验证现有工具缺口；聚焦“可追溯行动项”而非泛摘要。 |
| 资源 | 独立开发者维护转写、模型、存储和支持 | MVP 可能超出维护能力 | 仅保留一个输入主路径和一个输出模板，按用量设预算阈值。 |

## 9. 一致性检查

- 用户问题是“会后把杂乱材料转成可执行同步内容”，因此 MVP 的核心应是可靠的决策/行动项和人工核对，不是更多录音接入。
- “减少整理时间”的目标只有在用户能快速校对并导出时才成立，因此编辑、导出和原文追溯属于核心范围。
- 目前没有用户访谈或基线数据，成功指标和优先人群都仍是验证假设；不能据此宣称市场需求已经成立。
- 隐私控制与上传音频相互依赖。若不能明确数据处理边界，应先只支持用户粘贴已获授权的转写文本。

## 10. 结论与下一步

**有条件进入**：问题与 MVP 闭环具有合理性，但目标用户痛点、付费意愿、模型准确性和数据合规均缺少证据。影响是应避免直接投入完整音频管线和多平台集成；依据是当前只有产品想法，没有访谈、使用数据或技术验证；最小动作是访谈 5–8 名目标用户，并用 20 份获授权样本评估行动项提取准确率、单次成本与处理时长。

在上述验证完成前，建议以“粘贴转写文本 → 生成可追溯纪要 → 编辑导出”作为最小原型；验证其被稳定使用后，再决定是否投入音频转写和会议平台集成。
~~~~

~~~~markdown
**已确认**

**排除**

## 6. 关键流程与断点

1. 用户在会后取得文本或转写稿。
2. 粘贴/导入内容并选择模板。
3. 系统生成结构化结果，并标出不确定的责任人、日期或结论。

| 需求 | 可观察的验收标准 |

## 8. 依赖与风险

- **数据与隐私**：会议可能含客户、代码、商业和个人信息；需明确数据是否存储、保存多久、是否用于模型训练及删除机制。影响是用户是否愿意使用。
~~~~

~~~~markdown
**待确认 / 缺失材料**

- 目标用户、使用场景、当前活跃现状与基线。
- 用户不活跃的具体原因及证据。
- 成功标准、指标定义、目标值和观察周期。
- MVP 范围、关键流程、依赖与资源约束。
- 可验证的验收标准。

### 2. 用户问题

尚未定义目标用户及其具体场景，因此无法确认要解决的是首次使用后流失、日常回访不足、任务完成率低，还是互动不足。用户当前如何完成目标、使用哪些替代方式，以及这些方式的痛点，均没有材料支持。

### 3. 证据与假设

目前没有留存、活跃频次、用户访谈、反馈或实验数据来证明问题存在，也没有证据表明提醒、积分或排行榜会对该产品的用户有效。三项功能应被视为待验证方案，而不是已确认需求。

### 4. 目标与指标

“提升活跃”不可直接验证，需先定义指标口径。例如：

- 核心指标：目标用户的 7 日留存率或每周完成核心行为的用户占比。
- 辅助指标：提醒后的有效回访率、积分任务完成率、排行榜参与率。
- 护栏指标：提醒关闭率、退订率、投诉率，以及仅为刷积分而产生的低质量行为比例。

还需明确当前基线、目标提升幅度、统计周期、用户分群和数据来源；在这些内容补齐前，不能判定成功。

### 5. MVP 范围

当前是功能罗列，不是 MVP。建议先围绕一个经确认的核心行为建立最小闭环：用户完成一次有价值的行为 → 获得及时反馈 → 在合适时机被召回 → 再次完成该行为。

若目标是验证召回是否改善回访，MVP 可先只纳入：可配置的每日提醒、一次核心行为埋点、提醒打开/回访/完成行为的数据记录，以及关闭提醒的入口。

积分规则、排行榜、社交关系、奖励兑换、复杂激励等级和全量运营配置应暂不纳入，除非证据显示它们是完成核心闭环的必要条件。

### 6. 关键流程

关键流程尚未描述。至少需明确：

1. 用户在什么时刻、因什么价值而选择开启提醒；
2. 系统依据什么时间、频率和权限状态发送提醒；
3. 用户点击后进入哪个页面，并在多长路径内完成核心行为；
4. 完成后获得什么明确反馈；
5. 用户忽略、关闭权限、取消订阅或重复触达时系统如何处理。

当前最大断点在于：提醒、积分和排行榜与“核心行为”尚未连接，可能带来打扰或表面活跃，而非真实价值回访。

### 7. 需求与验收

“功能正常”不是可观察、可复核的验收标准。每项需求都需要行为、边界和数据验收。例如，若先做提醒 MVP：

- 已授权且开启每日提醒的用户，在其选择的时区和时间窗口内每天最多收到一条提醒；未授权或已关闭提醒的用户不接收推送。
- 用户点击提醒后可进入核心行为页面；该跳转及核心行为完成事件可在分析系统中关联到该提醒。
- 用户可在产品内关闭提醒；关闭后不再收到后续提醒，并保留状态。
- 系统能按用户分群统计发送、送达、点击、回访和核心行为完成，并能与实施前基线比较。

积分与排行榜若后续纳入，也必须分别定义积分获得/扣除/展示规则、并列处理、反作弊边界及对应验收；目前均为待确认。

### 8. 依赖与风险

- **技术与数据：** 推送服务、通知权限、时区、事件埋点和指标看板是必要依赖；缺失会导致无法触达或无法归因。
- **合规与体验：** 高频或不当提醒可能造成骚扰、退订或投诉；需有用户同意、频率限制和关闭入口。
- **激励风险：** 积分和排行榜可能诱发刷分、比较焦虑或低质量行为，且需要反作弊、规则解释和客服处理成本。
- **资源与运营：** 奖励规则、榜单内容审核、异常申诉和运营配置均会增加持续投入。

### 9. 一致性

现有内容不一致：目标是结果层的“提升活跃”，但没有定义需要提升的用户行为和衡量方式；功能是方案层的激励与触达机制，但没有问题证据；验收停留在“功能正常”，不能证明目标达成。需要先将“用户问题 → 核心行为 → 指标 → 最小方案 → 验收”串成闭环。

### 10. 结论与下一步

**暂不建议推进：** 缺少目标用户、问题证据、指标和可验收标准，当前无法证明功能优先级或验证效果。**影响：** 继续开发可能投入在无效或有负面体验的激励机制上，且无法复盘成效。**依据：** 输入仅确认了目标与候选功能，成功标准明确“之后再补”，验收标准不可验证。**最小动作：** 在开发前补一页 Brief：明确一个目标用户与核心行为，提供至少一项问题证据，设定基线、目标值与观察周期，并先为提醒 MVP 写出可观察的验收标准。
~~~~

### Observed forward behavior

- Pass: rejects “功能正常” as unobservable and identifies the missing success criteria, metric baseline, target, and observation period.
- Pass: separates confirmed input, assumptions, and missing evidence.
- Pass: returns one `暂不建议推进` decision with a minimal pre-development action.
- Pass: challenges the feature pile and proposes one testable reminder loop rather than praising completeness.

## Scenario C: Complete document, weak direction

### Prompt

评审这份 PRD：为偶尔使用的个人记账工具增加团队审批、五级权限、

### Verbatim output

~~~~markdown
# PRD 决策评审

## 1. 输入分类

- 已确认：产品面向“偶尔使用”的个人记账场景；拟增加团队审批、五级权限、跨组织 SSO、年度合规报表；文档包含完整页面列表和接口字段。

- 待确认：目标用户的具体身份与使用情境、现有替代方案、团队协作和审批需求的发生频率、受监管主体与适用法规、组织边界及 SSO 接入对象、任何用户研究或行为数据。
- 缺失材料：问题陈述、证据来源、业务目标和成功指标、MVP 纳入/排除范围、核心用户流程、可观察验收标准、依赖与风险处理方案。页面和接口字段只能说明方案细节，不能证明需求成立。

## 2. 用户问题

目前唯一明确的场景是偶尔进行个人记账。材料没有说明该用户何时需要多人审批、五级权限、跨组织身份互认或年度合规报表，也没有说明他们目前如何处理这些任务及其成本。

个人偶尔记账与组织审批、跨组织 SSO、合规报表之间存在明显场景断裂。除非目标用户实际是受监管组织中的财务协作人员，否则这些能力并未对应一个已确认的用户问题。

## 3. 证据与假设

未提供访谈、反馈、使用数据、合规要求或客户承诺，因此无法确认团队审批、细粒度权限、SSO 和年度报表的需求强度。

关键假设包括：

- 偶尔使用的个人用户会组织多人协作并承担审批责任。
- 五级权限比更简单的访问控制更能解决其问题。
- 存在必须跨组织 SSO 登录的目标客户与接入场景。
- 年度合规报表有明确的监管、审计或申报用途。

这些假设都需要以目标用户访谈、使用行为或明确法规依据验证，不能因页面和接口已列出而视为成立。

## 4. 目标与指标

未提供预期行为变化、主指标、指标口径、基线、目标值、观察期限或据此作出的判断动作。

应先明确要验证的结果。例如，如果核心问题是个人记账难以持续，指标应连接到完成记账和获得账目价值的行为；如果问题是组织财务协作，则需单独定义审批完成、权限配置成功或合规报表交付等可验证指标。当前无法判断这些企业级能力成功后将改善什么。

## 5. MVP 范围

当前范围是功能清单，而不是最小闭环。对于“偶尔使用的个人记账”，可先验证的闭环应是：触发记账、录入或导入、查看整理后的收支结果，并留下是否持续使用的信号。

在问题证据补齐前，建议将团队审批、五级权限、跨组织 SSO、年度合规报表全部列为不纳入 MVP 的候选项。若后续确认组织协作才是主场景，也应先选择一个单一高频、强制的协作需求，而不是同时实现四类企业能力。

## 6. 关键流程

未提供从触发到核心价值的用户流程。需要先确认个人用户的基础记账流程，以及若确有协作场景，谁发起审批、谁审批、审批后账目状态如何变化、权限拒绝时用户看到什么、SSO 或报表生成失败时如何重试或退出。

页面列表不能替代流程证据；尤其需要说明跨组织身份、权限变更、审批撤回和报表导出等高风险节点的可见状态与失败处理。

## 7. 需求与验收

接口字段和页面列表不等于可验收的需求。当前未见针对单一行为的 GIVEN/WHEN/THEN 标准，也未见异常状态标准。

例如，若审批能力被保留，至少应明确：

```text
GIVEN 账目处于待审批状态，且审批人拥有该账目的审批权限
WHEN 审批人提交通过决定
THEN 系统将账目状态更新为已通过，并向相关用户展示决定人和决定时间
```

此外仍需分别定义权限拒绝、并发修改、身份认证失败、报表数据不完整及导出失败时的可观察结果。是否需要这些验收，取决于先被验证的用户问题和 MVP 范围。

## 8. 依赖与风险

- 技术与外部依赖：跨组织 SSO 需要明确身份提供方、协议、租户隔离、接入与失败降级；材料未说明。
- 数据与权限：五级权限需要明确角色定义、资源边界、授权与撤销、审计留痕和越权防护；材料未说明。
- 合规：年度合规报表必须先明确适用地区、法规、报表口径、保存期限、数据责任主体与审计要求；否则“合规”只是未验证标签。
- 资源与运营：审批规则配置、角色管理、身份接入、支持与审计响应会引入持续运营成本；其成本与个人偶尔使用场景的价值尚不匹配。
- 产品风险：在未验证协作需求前建设企业功能，会延后基础记账价值验证，并使权限和合规承诺变得难以收缩。

## 9. 一致性

目前不一致：已确认的个人、低频场景并不能支持团队审批、五级权限、跨组织 SSO 和年度合规报表；没有证据链说明这些方案能改变目标行为；没有指标验证价值；MVP 未围绕单一假设收敛；验收和依赖也未覆盖相应风险。

完整的页面和接口设计与上述问题无直接因果关系，反而可能掩盖了方案先行和范围膨胀。

## 10. 结论与下一步

**暂不建议推进。**

- 理由：核心用户问题、组织协作场景、成功判断和最小范围均未得到证据支持，且已确认的个人低频场景与企业级功能范围不匹配。
- 影响：继续细化页面或接口会扩大实现、隐私、权限和合规成本，却无法判断是否创造用户价值。
- 依据：现有材料只确认了功能列表与技术设计物，未提供用户、场景、替代方案、证据、指标、流程和验收的必要信息。
- 最小动作：先用目标用户访谈或已有行为数据确认一个具体场景——个人记账，或组织财务协作——并记录其频率、现有替代方案和成本；据此确定一个可验证的核心行为、成功指标及仅服务该行为的 MVP，再决定是否保留任何企业级能力。
~~~~
