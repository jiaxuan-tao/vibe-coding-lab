# PRD 评审框架参考

本参考用于评审完整 PRD，或判断 Gate 结论存在争议时。它帮助把材料中的事实、假设和缺口转成可执行的产品判断；不替用户补写未经验证的 PRD 内容。

## 1. 用户问题

先回答：谁在什么情境下，因为什么具体阻碍而无法完成什么任务；现有替代方案为何不足。

- Strong：`独立开发者在客户会议后需手动从录音找出承诺和待办，常遗漏截止日期；目前用逐字稿和手工笔记。`
- Weak：`用户需要更智能的会议工具。`

向材料追问：

- 目标用户是否是可区分的人群，而不是泛称“所有用户”？
- 场景发生频率、现有做法、时间或错误成本是否有证据？
- 所提方案解决的是问题本身，还是仅描述一个功能？

没有访谈、行为数据、反馈记录或明确来源时，把问题强度标为假设或待确认，不推断为已确认痛点。

## 2. 证据、假设、待确认

- 已确认：材料提供可追溯来源、观察或已发生结果，例如访谈原话、数据口径、实验结果。
- 假设：合理但未经材料验证的判断，例如“提醒会提升留存”。
- 待确认：缺少作出判断所需的信息，例如当前留存基线、目标人群或授权边界。

不要把常识、行业惯例、模型推测或为了让 PRD 完整而补出的数字写成已确认。每个关键判断都说明其依据来自材料、是假设，还是需要确认。

## 3. 目标到指标的可追溯性

目标必须能对应一个可验证的结果，而非“提升活跃”“体验更好”之类的方向词。

检查链路：`用户问题 → 预期行为变化 → 主指标 → 口径/基线/目标值/期限 → 判断动作`。

- 可追溯：`会后遗漏待办` → `用户确认纪要中的待办` → `首次处理后确认待办比例`，并说明分母、当前值、目标和观察周期。
- 不可追溯：`提升活跃` → `做积分和排行榜`，没有目标人群、行为变化或指标口径。

若成功标准“之后再补”，应视为进入实现前的关键缺口，而不是可延后的文案工作。

## 4. MVP 切分与明确排除

MVP 只保留验证核心假设所需的最小闭环：触发、完成核心任务、获得价值、留下可观察信号。

逐项问：不做这一项，核心假设还能否被验证？若能，移到后续或列为排除项。范围应同时写出纳入项和不纳入项。

- 聚焦：先支持粘贴文本、生成待办、人工确认和导出，以验证用户是否采纳待办；明确排除音视频转写、多平台同步与团队权限。
- 功能堆砌：上传、转写、模板、搜索、分享、积分、排行榜、三方集成同时进入 MVP，却没有各自验证目的。

## 5. 可观察的用户流程与错误状态

核心流程用用户可观察的状态描述：触发条件、关键操作、系统可见结果、失败或中断后的去向。

示例：`用户粘贴会议文本并提交 → 系统显示处理中 → 生成带来源片段的待办 → 用户确认或更正 → 导出结果。`

至少检查输入无效、处理失败、信息不确定、权限拒绝或外部依赖失败时：用户看见什么、可以重试/撤销/退出什么。不以“异常处理完善”代替可观察结果。

## 6. 单一行为需求与 GIVEN/WHEN/THEN 验收

每条需求只描述一个可验证行为，避免把多个条件和结果揉成“功能正常”。验收需包含前提、动作和可观察结果。

```text
GIVEN 用户已粘贴有效会议文本
WHEN 用户提交整理请求
THEN 系统显示生成的待办及其来源片段
```

反例：`系统应正常生成高质量纪要。`其中“正常”和“高质量”没有观察方法。需要另列低置信度、无待办或生成失败时的行为。

## 7. 依赖、隐私、权限与不可逆影响

记录每个关键依赖的提供方、输入输出、失败影响和替代/降级方式。对数据和外部动作，确认：

- 是否收集、保存、传输或用于训练敏感内容；保留多久，谁可访问，如何删除。
- 是否需要录音、分享、导出或第三方同步的授权与权限范围。
- 是否会发送通知、创建外部任务、公开数据、扣费或删除内容等不可逆影响；是否有用户确认、撤销或预览。

不要以“已加密”“支持权限”笼统通过；材料未说明时标待确认并指出影响。

## 8. 一致性检查与 Gate 决策

核对下列关系是否自洽：目标用户和场景是否支持用户问题；方案是否直达问题；指标是否验证方案带来的行为变化；MVP 是否只服务该验证；验收是否覆盖流程与风险。

结论只选一个：

- 可进入设计：核心问题、验证目标、最小范围和关键风险已有足够依据；仍可列非阻塞待确认项。
- 有条件进入：方向成立但存在可在进入设计前以最小动作补齐的关键缺口。
- 暂不建议推进：用户问题、成功判断或范围基础缺失，继续细化方案只会放大假设。

示例：若“偶尔个人使用”是唯一已知场景，PRD 却要求企业 SSO、组织权限和审计，指出场景与企业范围不匹配；不要因目录完整而认可推进。若目标只是“提升活跃”、成功标准待补且验收为“功能正常”，结论应给出一个 Gate 和最小补充动作，而非继续扩写功能。

## 9. 常见失败模式

- Solution-first：先定 AI、积分或排行榜，再倒推用户问题。回到场景、替代方案与证据。
- Feature pile：功能列表代替验证范围。用核心假设削减到最小闭环，并写排除项。
- Vanity metric：展示量、注册量等不能说明核心价值。改用与问题和目标行为相连的指标。
- Hidden dependency：第三方、数据、权限或运营前提没有显式记录。写清失败影响和确认动作。
- AI-completed fiction：AI 为完整性虚构用户痛点、数字、范围或访谈。将其保留为假设或待确认。
- Untestable acceptance：用“功能正常”“体验良好”作验收。改为单一行为的 GIVEN/WHEN/THEN 与错误状态。
