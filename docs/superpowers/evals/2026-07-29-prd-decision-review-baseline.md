# Baseline Evaluation

## Environment
- Skill available: no
- Evaluation date: 2026-07-29

## Scenario A: Vague idea
### Prompt
帮我写一份 PRD：给独立开发者做一个 AI 自动整理会议记录的工具。

### Verbatim output
```markdown
# PRD：AI 会议记录自动整理工具

## 1. 产品概述

### 1.1 产品名称

暂定名：MeetingFlow AI

### 1.2 背景与问题

独立开发者往往同时承担产品、开发、运营和客户沟通等工作。每天参与需求讨论、客户访谈、协作会议后，会议记录通常散落在录音、聊天工具、文档和个人笔记中，后续整理需要大量时间。

现有通用会议工具通常偏向企业团队，功能复杂、价格较高，且不一定适合独立开发者的工作方式。用户真正需要的不是一份逐字稿，而是能快速执行的结论：做什么、谁来做、什么时候完成、哪些问题需要继续确认。

### 1.3 产品定位

一款面向独立开发者的 AI 会议记录整理工具。用户上传会议音频、视频或文本后，系统自动生成结构化会议纪要、待办事项、决策结论和后续跟进内容，并可同步到常用工作工具。

### 1.4 目标用户

- 独立开发者：与客户、合作伙伴或兼职成员沟通需求与项目进度。
- 小型创业团队的创始人：需要快速把会议结论转化为任务。
- 自由职业开发者／顾问：需要保留客户沟通记录，并整理交付范围和下一步。

### 1.5 核心价值主张

“会议结束后 3 分钟，获得可以直接执行的项目结论。”

产品帮助用户减少手工整理会议记录的时间，避免遗漏任务与承诺，并让项目沟通有可追溯的上下文。

---

## 2. 产品目标

### 2.1 业务目标

- 验证独立开发者是否愿意为 AI 会议整理能力付费。
- 建立从“上传会议内容”到“执行后续任务”的高频使用闭环。
- 通过轻量集成提高留存，而非依赖复杂的企业协同功能。

### 2.2 用户目标

- 在会议结束后快速了解讨论结论。
- 自动识别待办、负责人、截止时间和风险项。
- 能方便地修改、分享和沉淀会议记录。

### 2.3 成功指标

| 指标 | 定义 | 初期目标 |
| --- | --- | --- |
| 首次价值达成率 | 新用户首次上传后成功生成纪要的比例 | ≥ 70% |
| 纪要查看率 | 已生成纪要中被用户打开查看的比例 | ≥ 80% |
| 编辑采纳率 | 用户至少编辑、确认或导出一次纪要的比例 | ≥ 40% |
| 周留存率 | 首周用户在次周再次处理会议的比例 | ≥ 25% |
| 单次处理时长 | 从上传完成到纪要生成完毕的中位时长 | ≤ 3 分钟（30 分钟音频） |

---

## 3. 用户场景与需求

### 场景一：客户需求会议后整理

用户与客户进行了 45 分钟的视频会议，讨论了新功能范围、交付日期和需要客户补充的材料。会后用户上传录音，希望马上得到项目摘要、双方确认的需求、待办事项和待确认问题。

### 场景二：小团队周会跟进

两三人的远程团队完成周会后，需要将本周进展、阻塞问题和下周任务同步到任务管理工具。用户希望系统能自动识别负责人和截止时间，并在导出前快速校对。

### 场景三：个人语音笔记整理

用户在通勤时录下灵感或复盘语音，希望将其转为清晰的项目笔记和可执行任务，而非只得到逐字文本。

---

## 4. MVP 功能范围

### 4.1 会议内容导入

**用户故事**：作为独立开发者，我希望上传录音或粘贴会议文本，以便让 AI 自动整理内容。

功能要求：

- 支持上传 MP3、M4A、WAV、MP4 文件。
- 支持直接粘贴文本记录。
- 显示文件格式、大小、预计处理时间和处理状态。
- MVP 限制：单个文件最长 90 分钟、最大 500MB。
- 用户可填写会议标题、日期、参与者和会议类型。

### 4.2 转写与说话人识别

**用户故事**：作为用户，我希望获得可阅读的原始会议内容，以便核对 AI 总结是否准确。

功能要求：

- 自动将音视频转为带时间戳的文本。
- 尽可能区分不同说话人，默认使用“发言人 1／2／3”。
- 用户可手动重命名发言人。
- 支持中文和英文，允许中英混合内容。
- 转写完成后用户可搜索关键词并跳转到对应段落。

### 4.3 AI 结构化纪要

**用户故事**：作为用户，我希望系统自动输出重点结论，而不是阅读整段逐字稿。

纪要默认包含：

- 会议摘要：3–5 条关键结论。
- 讨论主题：按主题归纳主要观点与上下文。
- 已达成决策：明确标注已确认事项。
- 待办事项：任务内容、负责人、截止时间、来源片段。
- 待确认问题：尚未决定、信息不足或存在分歧的问题。
- 风险与阻塞：可能影响项目进度、范围或成本的事项。

生成时用户可选择会议模板：客户沟通、产品需求、项目周会、访谈记录、自由总结。MVP 提供默认模板与以上 4 个预设模板。

### 4.4 人工校对与编辑

**用户故事**：作为用户，我希望可以快速修正 AI 输出，避免把错误信息发给客户或团队。

功能要求：

- 纪要各模块支持直接编辑、删除和新增内容。
- 待办项可编辑负责人、截止时间和状态。
- 每条 AI 提取的待办和决策可查看原始转写引用。
- 用户可标记“AI 判断错误”，用于后续优化。
- 自动保存编辑内容，并显示最后更新时间。

### 4.5 导出与分享

**用户故事**：作为用户，我希望将整理结果发送给客户或同步到工作流中。

功能要求：

- 支持复制为 Markdown、纯文本。
- 支持导出为 Markdown 文件和 PDF。
- 支持生成只读分享链接，可设置过期时间。
- MVP 集成一个任务工具（建议优先支持 Notion 或 Linear），将已确认待办导出为任务。

### 4.6 会议记录管理

**用户故事**：作为用户，我希望以后能找到某次会议的结论和承诺。

功能要求：

- 首页展示最近会议及处理状态。
- 支持按标题、参与者、日期、标签和内容关键词搜索。
- 支持标签与归档。
- 支持删除会议及相关音频、转写和纪要数据。

## 5. 关键流程

1. 用户注册／登录后进入首页。
2. 用户点击“新建会议”，上传文件或粘贴文本。
3. 用户填写基础信息并选择纪要模板。
4. 系统完成转写、说话人识别与 AI 总结。
5. 用户在纪要页查看摘要、决策、待办和待确认问题。
6. 用户修改或确认重点内容。
7. 用户复制、导出、分享纪要，或将待办同步到任务工具。
8. 会议记录保存至历史列表，后续可搜索和复用。

## 6. 信息架构

- 首页／会议列表
  - 最近会议
  - 新建会议
  - 搜索与筛选
- 新建会议页
  - 文件上传／文本粘贴
  - 基础信息
  - 模板选择
- 会议详情页

  - 待办事项
  - 原始转写
  - 导出与分享
- 设置页
  - 账户与订阅
  - 集成设置
  - 数据与隐私

## 7. 非功能性要求

### 7.1 性能

- 30 分钟音频的端到端处理时间应尽量控制在 3 分钟以内。
- 页面基础操作响应时间不超过 2 秒。
- 处理失败时应明确显示失败原因，并允许用户重新提交。

### 7.2 隐私与安全

- 上传文件与生成内容采用传输加密和存储加密。
- 默认不将用户会议内容用于模型训练；如未来需要，应单独取得明确授权。
- 用户可永久删除会议数据。
- 分享链接默认仅限持有链接者查看，并支持设置访问期限。
- 在上传前提示用户：应确保其拥有录音、上传和处理相关内容的合法授权。

### 7.3 准确性与风险提示

- AI 输出区域应明确标注“建议人工确认”。
- 对负责人、日期、金额、承诺等高风险实体，在信息不明确时显示“待确认”，不应强行猜测。
- 对无法识别的音频和低置信度转写，提示用户检查原始内容。

## 8. 商业模式初步假设

采用免费试用加订阅模式：

- 免费版：每月 3 次会议处理、基础纪要与 Markdown 导出。
- Pro 版：更多处理时长、高级模板、分享链接、任务工具集成和更长的数据保存期。
- 可选按量包：面向低频但单次会议较长的用户。

定价应在验证用户会议频率、音频处理成本和可接受付费意愿后确定。MVP 阶段更重要的是验证用户是否愿意持续上传并使用结构化待办结果。

---

## 9. 暂不纳入 MVP 的功能

- 实时会议机器人自动入会。
- 多语言实时字幕与翻译。
- 企业级组织、权限、审计与 SSO。
- 复杂 CRM、日历和多任务平台集成。
- 自动发送邮件或自动创建外部任务（MVP 先采用用户确认后导出）。
- 深度会议质量分析、情绪识别或绩效评估。

这些功能会显著增加技术、隐私和集成复杂度，且不是验证核心价值所必需。

---

## 10. 关键假设与待验证问题

1. 独立开发者的痛点是“会后整理与跟进”，而非单纯“录音转文字”。
2. 用户更看重待办和决策的准确性，而不是摘要写得多优美。
3. 用户愿意上传客户会议内容的前提是隐私政策清晰、可删除且不用于训练。
4. 首批用户最常见的输入方式需要验证：上传录音、导入视频会议录制，还是粘贴文本。
5. 首个第三方集成应根据目标用户现有工作流确定；不要在没有验证前同时做多个集成。
6. 需要测试不同模板对用户采纳率和编辑量的影响。

---

## 11. 版本规划

### V0：可用原型

- 文本粘贴输入。
- AI 生成摘要、决策、待办和待确认问题。
- 在线编辑与 Markdown 复制。

### V1：MVP 上线

- 音视频上传与转写。
- 预设纪要模板。
- 会议历史、搜索、分享和基础导出。
- 单一任务工具集成。
- 基础订阅与使用额度。

### V2：验证后的增强

- 视频会议平台自动导入。
- 更可靠的说话人识别与自定义词汇。
- 项目维度的会议关联、任务追踪和上下文问答。
- 更丰富的集成与团队协作能力。

---

## 12. 验收标准

- 用户可以成功上传符合限制的音视频文件或粘贴文本。
- 系统能生成可查看的转写和结构化会议纪要。
- 纪要至少包含摘要、决策、待办、待确认问题四个核心区块。
- 用户可以编辑每个核心区块，并保存修改。
- 用户可以复制 Markdown、导出文件或生成分享链接。
- 用户可以在历史记录中搜索、查看和删除会议。
- 在处理失败、低置信度识别或信息不明确时，系统提供清晰提示，不将不确定信息包装为确定结论。
```

### Observed failures
- 将未提供的用户痛点、目标用户扩展、产品定位、功能范围、指标阈值和商业模式等内容写为 PRD 事实；虽在后文标注部分“假设”，但此前大量结论未区分证据来源。
- 未给出进入下一阶段的明确 gate 决策；直接开始完整 PRD 撰写。
- 在验证问题与范围方向前先完成了详细结构、页面、接口相关功能和验收描述。
- 用户仅请求“写一份 PRD”，输出已直接重写并扩展整个文档，未提供确认或最小下一步。

## Scenario B: Incomplete PRD
### Prompt
评审这份 PRD：目标是提升活跃；功能包括每日提醒、积分、排行榜；
成功标准之后再补；验收标准是功能正常。

### Verbatim output
```markdown
# PRD 评审意见

当前 PRD 尚不足以进入开发，核心问题是目标、方案和验证方式都过于笼统，无法判断做什么、为何做以及是否有效。

## 主要问题

1. **目标不可衡量**："提升活跃"没有定义具体指标。需要明确是 DAU、WAU、留存率、人均启动次数、连续活跃天数，还是其他指标；同时给出当前基线、目标值与达成期限。
2. **用户与场景缺失**：没有说明目标用户是谁、他们为什么不活跃，以及每日提醒、积分、排行榜分别解决什么问题。三项功能可能对不同人群有效，也可能造成打扰或竞争压力。
3. **功能范围不完整**：
   - 每日提醒：触发时间、频率、渠道、时区、用户关闭入口、文案与触发条件均未定义。
   - 积分：获得与消耗规则、积分上限、是否过期、作弊防护、积分用途未定义。若积分不能兑换价值，激励效果可能有限。
   - 排行榜：排名口径、周期、范围、隐私展示、并列规则、异常数据处理、是否允许退出未定义。
4. **缺少效果验证**：成功标准"之后再补"会导致上线后无法判断是否应继续投入。应在开发前定义主指标、护栏指标和实验或对照方案。
5. **验收标准不可执行**："功能正常"不是验收标准。需要把每个关键流程、异常流程、权限与数据口径写成可验证的条件。
6. **风险未覆盖**：提醒可能增加关闭通知或卸载；积分和排行榜可能诱发刷分、低质量行为、挫败感与隐私投诉。应有频控、退出机制、反作弊和监控方案。

## 建议补齐的最小决策

- 活跃的业务定义、基线、目标值和观察周期。
- 目标用户分群及优先场景。
- 三项功能的优先级与假设：先验证哪一种机制，为什么。
- 积分规则及可感知价值；排行榜的隐私与公平规则；提醒的频率控制与退订方式。
- 上线方式：灰度范围、A/B 实验或前后对比方法、回滚条件。
- 成功标准：例如目标用户 28 天内的周活跃率提升 X%，且通知关闭率、投诉率、次日留存不劣化超过预设阈值。

## 可验收标准示例

- 用户可在设置中独立开启、关闭每日提醒，并能在设定时区的指定时间收到不超过每日一次的提醒。
- 用户完成定义的有效行为后，积分按公开规则准确到账；重复、异常或无效行为不重复计分。
- 排行榜按明确周期和排名口径更新，用户可选择不公开昵称或退出榜单，退出后不再展示其信息。
- 埋点可准确记录提醒送达、点击、有效行为、积分变动、排行榜曝光与互动，用于计算预先定义的活跃指标。
- 灰度期间可按预设阈值监控负面指标；达到回滚条件时可关闭提醒、积分或排行榜入口而不影响核心功能。

结论：建议先补齐指标、用户问题、激励规则、隐私与反作弊要求，再确定开发范围。若资源有限，应优先选择一个假设最强、可独立验证的机制进行小流量实验，而非同时上线三项功能。
```

### Observed failures
- 没有明确地区分已知事实、推断与待确认假设；例如对潜在负面影响及功能效果作出合理但未标注来源的推断。
- 有“尚不足以进入开发”的结论，但未使用预定义的三选一 gate 决策形式。
- 未先对用户问题或三项机制的方向作出单一优先级判断，就给出了大批详细规则与验收标准示例。
- 作为评审输出，未重写整份 PRD；验收标准示例属于补充建议，而非完整重写。

## Scenario C: Complete document, weak direction
### Prompt
评审这份 PRD：为偶尔使用的个人记账工具增加团队审批、五级权限、
跨组织 SSO 和年度合规报表。文档包含完整页面列表和接口字段。

### Verbatim output
```markdown
这份 PRD 的问题不在页面和接口字段不完整，而在于方案与产品场景明显失配：一个“偶尔使用”的个人记账工具，被一次性引入了团队审批、五级权限、跨组织 SSO 和年度合规报表，复杂度远超核心需求的价值。

结论：不建议按当前范围进入开发，应退回做需求收敛与价值验证。

主要问题：

1. 用户与场景不一致
   - 个人记账的核心任务通常是快速记录、查看收支、预算和回顾。团队审批与五级权限服务的是多人协作、费用报销或企业财务管理，PRD 没有说明这些用户是否真实存在、占比多少、使用频率如何。
   - “偶尔使用”意味着用户对操作摩擦很敏感。登录、组织切换、审批流和权限配置会显著降低完成一次记账的效率。

2. 缺少价值与优先级判断
   - 文档描述了“做什么”，但没有说明每项能力解决什么已验证的问题、面向谁、成功标准是什么。
   - 四项能力都属于高成本能力，且相互耦合。没有明确 MVP、上线顺序和不做什么，容易形成一次性大项目。

3. 方案过度设计
   - 五级权限通常会带来角色定义、资源授权、数据隔离、审计、异常处理和后台配置等长期维护成本。除非已有明确的多角色协作模型，否则应先从少数预置角色开始。
   - 跨组织 SSO 需要明确企业客户、身份提供商范围、账号合并、离职/禁用、租户隔离和安全责任。对个人工具而言，这一能力缺乏合理前提。
   - 年度合规报表必须明确适用地区、法规、报送主体、数据留存期限、审计要求，以及“报表导出”还是“合规保证”。否则“合规”是无法验收的模糊承诺。

4. 页面与接口先于决策
   - 完整页面列表和字段只能证明实现细节被展开，不能证明需求成立。当前应先补充用户、场景、价值和边界，再决定页面、接口及数据模型。

建议的重构方向：

- 先确认目标产品究竟是个人记账，还是面向小团队的费用/财务协作产品；两者应拆成不同的产品定位和路线图。
- 若仍以个人记账为核心，本期优先改善记录效率、自动分类、账单提醒和年度收支总结；团队、SSO、复杂权限和合规报表不应进入当前版本。
- 若要服务团队，先用一个最小可验证版本验证需求：固定的管理员/成员两类角色、简单共享账本或报销确认，不做跨组织 SSO、不做可配置五级权限，也不宣称合规。
- 对每个候选能力补充：目标用户、触发场景、现有替代方案、预期频率、业务价值、风险、验收指标和不在范围内的内容。

建议在 PRD 中补齐以下关键问题后再评审：

1. 哪类用户提出了团队协作需求？有多少人、频率多高？
2. 审批的对象和结果分别是什么？是否必须留痕？
3. 五个权限等级各自对应哪些真实职责？是否能合并为两到三个固定角色？
4. 哪些客户或组织要求 SSO？支持哪些身份提供商，为什么现在必须支持？
5. “年度合规报表”具体对应哪项法规、哪个地区和哪种法律责任？
6. 如果只交付一个版本，哪项能力最能验证需求，成功指标是什么？

在这些问题没有答案前，建议暂停 UI 和接口细化，先完成产品定位与 MVP 决策。
```
