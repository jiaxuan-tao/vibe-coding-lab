# 台球追分计分台 Design Specification

## 1. Product Purpose

“台球追分计分台”是一款手机优先的多人实时追分工具。它服务于
2–6 名球友共用一台手机的线下台球场景，让用户在每局进行过程中
快速记录犯规与得分事件，并在连续多局后获得可信的累计积分、事件
流水和结果统计。

产品核心不是教授台球规则，也不是正式赛事裁判系统，而是把纸笔或
口头记账替换为一套快速、可撤销、可配置、不会算错的现场计分流程。

## 2. Confirmed Product Decisions

- 产品名称：`台球追分计分台`
- 英文项目名：`Pool Chase Score`
- 仓库目录：`pool-chase-score`
- 形态：手机竖屏优先的响应式 Web/PWA
- 使用方式：一台手机由现场玩家共用
- 参与人数：2–6 人，默认 3 人
- 玩家名称：可自定义，并可保存为常用球友
- 默认规则：常见 `1 / 4 / 7 / 10` 模板，同时支持空白模板
- 规则范围：开始“今日追分”前设置，后续各局沿用同一份规则快照
- 计分时机：犯规等局内事件实时计分，不能只在一局结束后结算
- 联动方式：一次操作更新所有相关玩家，而不是逐人手动加减
- 顺序方式：每局开始前设置玩家顺序；系统不推测当前击球者
- 局间积分：每局结束后累计积分不清零，只归档当前局事件
- 结束方式：“今日追分”仅由用户手动结束，不设置目标分提醒
- 持久化：数据仅保存在当前浏览器，不需要账号、后端或云同步
- 结果输出：结束后生成本地成绩单图片
- 金额边界：只记录积分，不提供金额换算、支付或真钱结算

## 3. Domain Terminology

为避免“场、局、把”混用，产品统一使用以下术语：

- `今日追分`：从设置玩家和规则开始，到两三个小时后手动结束的
  一次完整活动。
- `第 N 局`：从本局开球到出现终局结果或被手动作废。
- `局内事件`：犯规、让杆犯规等不会自动结束当前局的计分动作。
- `终局事件`：普胜、小金、大金、黄金九等会结算并结束当前局的
  结果动作。
- `玩家顺序`：本局用于判断上家、下家和结算关系的循环顺序，
  不代表系统知道当前击球者。
- `累计积分`：玩家从今日追分开始至当前时刻的总积分。

## 4. Product Boundaries

### Included

- 新建、继续和结束一次“今日追分”。
- 2–6 名玩家与常用球友名单。
- 初始积分的 `100 / 0 / 自定义` 快捷设置。
- `1 / 4 / 7 / 10` 默认规则和空白规则。
- 事件名称、分值、结算类型、是否终局的配置。
- 每局玩家顺序设置和下一局顺序建议。
- 局内实时联动计分。
- 终局自动结算、结束本局并进入下一局准备。
- 最近事件、低强调度撤销、单条修改和删除。
- 跨局累计积分、本局记录和完整历史。
- 刷新或误关后的现场恢复。
- 最终排名、事件统计和成绩单图片。
- 添加到手机桌面、离线打开和响应式布局。

### Excluded

- 账号、登录、云同步和多人实时联网。
- 自动识别击球人、摄像头识别或语音裁判。
- 台球规则教学、犯规判定和正式赛事裁判功能。
- 地理位置、球房、预约和社交功能。
- 下注、金额换算、支付、输赢款项和任何真钱结算。
- 依赖远程 AI、数据库或付费服务。

## 5. Primary User Flows

### Flow A: Start Today’s Session

1. 用户打开首页，选择“开始今日追分”。
2. 从常用球友中选择或新增 2–6 名玩家。
3. 使用全员 100、全员 0，或分别设置初始积分。
4. 选择 `1 / 4 / 7 / 10` 默认模板或空白模板。
5. 查看并编辑每个事件的名称、分值和结算关系。
6. 拖动排列第一局玩家顺序。
7. 页面用真实玩家姓名预览典型结算，用户确认后开始第 1 局。

### Flow B: Record an In-Rack Event

1. 用户点击发生事件的玩家，玩家行放大并高亮。
2. 用户点击“犯规”等局内事件。
3. 规则引擎根据本局顺序和规则快照计算所有玩家的积分变化。
4. 界面立即更新累计积分，并用一句话显示结算结果。
5. 事件进入本局流水；本局继续。
6. 若发生误点，用户可使用低强调度的撤销图标，或在流水中修改、
   删除该条事件。

### Flow C: Record a Rack Result

1. 用户选择获胜者。
2. 点击“普胜、小金、大金、黄金九”等终局事件。
3. 若该规则需要指定主要负方，界面只追加一次玩家选择，不要求
   用户逐人录入分值。
4. 系统完成联动结算，将该事件写入流水并结束当前局。
5. 结果面板显示本局积分变化和下一局建议顺序。
6. 用户可以撤销终局结果，也可以调整顺序后开始下一局。
7. 新局清空局内事件视图，但保留今日累计积分和历史记录。

### Flow D: End Today’s Session

1. 用户从次级菜单选择“结束今日追分”。
2. 页面明确区分“结束今日追分”和“结束当前局”，并要求确认。
3. 系统保存最终积分、排名、局数、时长和事件统计。
4. 用户可以查看每局记录、生成成绩单图片或开始一次新的追分。
5. 新的追分可以沿用常用球友和规则模板，但创建独立记录并重新
   使用设定的初始积分。

## 6. Rule Model

### 6.1 Rule Snapshot

规则在“今日追分”开始时复制为不可变快照。进行中不允许直接修改
该快照，避免同一种事件在前后局使用不同算法。

如用户确需更改规则，应结束当前追分并新建一次记录。历史记录始终
保留当时实际使用的规则，不引用可能被后续修改的模板。

### 6.2 Settlement Types

规则编辑器不暴露数学公式，而提供三种可理解的结算方式：

1. `顺序转分`
   - 从选中玩家向其上家或下家转移设定分值。
   - 适合普通犯规等依赖玩家顺序的事件。
2. `两人转分`
   - 在事件发生时选择得分者和主要负方。
   - 得分者增加设定分值，主要负方扣除相同分值。
   - 适合普胜、小金等只涉及两人的结算。
3. `其余玩家共同给分`
   - 选择获胜者，其余所有玩家各扣除设定分值，获胜者获得扣分
     总和。
   - 适合大金、黄金九等多人共同结算。

所有结算默认保持总积分守恒。规则预览用真实姓名展示，例如：

`王强 +20 · 李明 -10 · 张伟 -10`

### 6.3 Default 1 / 4 / 7 / 10 Template

默认模板用于快速开始，不宣称是所有地区唯一规则：

| 事件 | 默认分值 | 结算方式 | 是否结束本局 |
| --- | ---: | --- | --- |
| 犯规 | 1 | 犯规者向上家转分 | 否 |
| 普胜 | 4 | 主要负方向获胜者转分 | 是 |
| 小金 | 7 | 主要负方向获胜者转分 | 是 |
| 大金 | 10 | 其余玩家共同给获胜者 | 是 |
| 黄金九 | 4 | 其余玩家共同给获胜者 | 是 |

用户可在开始前修改名称、分值、结算方式、方向和终局属性，也可
关闭扩展事件或新增自定义事件。

### 6.4 Value Limits

- 玩家人数：2–6。
- 初始积分：`-9999` 至 `9999`，仅允许整数。
- 单次事件分值：`1` 至 `999`，仅允许整数。
- 事件数量：1–12 个，其中至少保留一个终局事件。
- 玩家名称：1–10 个可见字符，同一场内不可重复。

边界控制的目的不是限制地方玩法，而是防止误输入导致移动端布局
失控或分数溢出。

## 7. Player Order

- 顺序使用循环列表表示，并明确标注当前局第 1、2、3…位。
- 第一局由用户拖动设置。
- 系统不展示“当前击球人”，也不自动轮转击球状态。
- 终局后，下一局建议顺序为：
  1. 获胜者排第一；
  2. 主要负方排第二；
  3. 其他玩家按上一局相对顺序排列。
- 没有主要负方的多人结算中，获胜者排第一，其他玩家保持上一局
  相对顺序。
- 建议顺序在开始下一局前始终可拖动修改。

## 8. Data and Score Integrity

分数采用事件流水驱动，而不是把每次点击直接固化为一个无法追溯
的总数。

### Session

- 会话 ID、状态、开始/结束时间。
- 玩家、颜色、初始积分。
- 规则快照。
- 当前局编号和当前玩家顺序。
- 已结束的局与当前局。

### Score Event

- 事件 ID、发生时间、所属局。
- 规则 ID 和当时显示名称。
- 操作玩家、目标玩家。
- 每名玩家的积分变化 `deltas`。
- 生效、已撤销或已替换状态。
- 是否终局及终局后的建议顺序。

### Derived Score

任意时刻的累计积分均由：

`初始积分 + 所有有效事件的 deltas`

重新计算。撤销、修改和删除只改变事件状态并重新计算，不直接手工
覆盖玩家总分。这样可保证历史、统计和界面总分一致。

## 9. Interface Architecture

### Home

- 产品名和简短状态。
- 主操作：“开始今日追分”。
- 存在未结束记录时优先显示“继续今日追分”。
- 历史记录和常用球友作为次级入口。
- 使用一张本地台球桌/台球视觉资产建立产品识别，不做营销式 Hero。

### Setup

- 四个连续步骤：玩家、初始分、规则、第一局顺序。
- 使用顶部进度和底部固定主按钮，不嵌套卡片。
- 规则使用可展开行，每行直接显示“谁给谁多少分”。
- 完成前执行重名、人数、规则和分值校验。

### Score Console

- 视口高度使用 `100dvh`，主计分界面不依赖页面整体滚动。
- 顶部：第 N 局、今日用时、低强调度更多菜单。
- 中部：2–6 个玩家计分行，当前选择使用尺寸、边框和文字三重状态
  区分，不只依赖颜色。
- 玩家行稳定显示顺序、姓名、累计积分和相对初始分变化。
- 底部：局内事件和终局事件分组排列，保持至少 44px 点击区域。
- 6 人场景允许玩家列表区域内部滚动，但计分操作区保持可见。
- 最近三条事件位于操作区上方；撤销使用小型回退图标和文字提示，
  不使用大按钮或高饱和主色。
- 点击事件后不增加全屏确认步骤；使用即时结算提示和可恢复撤销，
  保持现场操作速度。

### Rack Result

- 终局后以底部面板显示本局结果，不跳转到完全不同的页面。
- 展示获胜者、本局各玩家变化和下一局建议顺序。
- 主操作：“开始下一局”。
- 次级操作：“撤销本局结果”“调整顺序”。

### History and Summary

- 历史列表按日期显示参与者、局数、时长和最终第一名。
- 详情页包括最终排名、每局结果、事件分类统计和完整流水。
- 成绩单使用方形或竖版 Canvas 生成，包含产品名、日期、玩家排名、
  分数变化和主要事件统计。
- 分享图不包含完整流水、设备信息或任何金额。

## 10. Visual Direction

采用“台球厅机械计分台”方向：

- 主色为深台呢绿、近黑木色和暖白。
- 铜金色只用于当前选择、局数和关键排名；危险/删除使用克制红色。
- 玩家使用高区分度色签和首字母标识，不要求上传头像。
- 分数使用宽体等宽数字，玩家姓名使用清晰的中文无衬线字体。
- 背景可以使用轻微台呢纹理，但不能降低文字对比度。
- 控件使用明确边框与轻微实体阴影，不使用玻璃拟态、发光渐变球或
  装饰性卡片堆叠。
- 主计分页不出现产品说明、操作教程或大段功能介绍。
- 图标使用 Lucide 图标体系；不手绘近似图标。
- 视觉资产全部本地化，离线状态不依赖第三方图片 CDN。

## 11. Motion and Feedback

- 玩家选择使用 120–180ms 的尺寸与边框过渡。
- 计分后对应分数短暂上浮或闪动，但布局尺寸不变化。
- 终局面板使用短距离底部进入，不遮挡结果。
- 撤销后提供 3 秒的“已撤销 / 恢复”轻提示。
- 触摸设备在支持时使用轻量振动反馈；失败时静默降级。
- `prefers-reduced-motion: reduce` 时关闭分数跳动和面板位移动画。
- 声音不是核心需求，首版不加入音效，避免球房环境中产生干扰。

## 12. Persistence and Recovery

- 使用带版本号的 `localStorage` 保存小体量结构化数据。
- 每次有效事件、局结束、顺序确认和设置完成后立即保存。
- 打开页面时优先检测未结束记录并提供继续入口。
- 数据解析失败时保留损坏备份并回退到安全状态，不让页面白屏。
- 历史默认保留最近 50 次今日追分；用户可以单条删除或清空全部。
- 常用球友和规则模板独立保存，删除历史不影响模板。
- Service Worker 缓存应用壳和本地资产，更新时提示刷新，不在计分
  过程中自动替换页面。

## 13. Technical Architecture

项目采用无后端、低依赖的前端实现，并优先沿用仓库现有静态项目
结构：

- `index.html`：语义结构、各应用视图和对话框。
- `styles.css`：设计系统、响应式布局和状态动画。
- `rules.js`：规则模板、结算类型和纯函数计分引擎。
- `session.js`：今日追分、局、顺序和事件状态机。
- `storage.js`：版本化本地存储、迁移和容错。
- `share.js`：Canvas 成绩单生成和系统分享。
- `app.js`：视图渲染、事件绑定和应用编排。
- `manifest.webmanifest` 与 `sw.js`：可安装和离线应用壳。
- Node.js 原生测试：规则引擎、状态机、持久化和页面契约。
- Playwright：手机端核心流程、恢复、撤销和视觉布局验证。

运行时不需要远程 API。若现有仓库工具链可以复用，则只使用其
开发依赖；不为该项目引入重量级框架。

## 14. Error and Edge States

- 玩家不足、名称重复或为空时不能开始。
- 没有终局事件时不能保存规则。
- 事件需要主要负方时，不能选择获胜者本人。
- 当前未选择玩家时，事件按钮保持禁用并说明原因。
- 已结束本局时不能继续添加局内事件。
- 已结束今日追分后记录只读。
- 连续快速点击通过操作锁防止重复记分。
- 重新载入后恢复到最后一次完整保存，不应用半完成选择。
- 删除或修改历史事件后，总分、局统计和结果图必须同时重算。
- 分享 API 不可用时回退为下载 PNG。
- Service Worker 更新失败不影响当前计分。

## 15. Accessibility

- 所有操作可通过键盘完成。
- 点击区域至少 44×44px。
- 选中、禁用、正负分变化不只依赖颜色。
- 分数和关键按钮满足 WCAG AA 对比度。
- 对话框和底部面板管理焦点，关闭后返回触发元素。
- 图标按钮提供可访问名称和 tooltip。
- 动态计分结果通过温和的 `aria-live` 区域播报。

## 16. Testing Strategy

### Unit Tests

- 三种结算类型在 2、3、6 人场景下保持积分守恒。
- 上家/下家循环边界正确。
- `1 / 4 / 7 / 10` 默认模板产生预期 deltas。
- 撤销、恢复、修改和删除后总分重新计算正确。
- 终局事件关闭当前局，局内事件不会关闭。
- 下一局建议顺序在有/无主要负方时正确。
- 规则、玩家名称和数值边界校验。
- 存储损坏、旧版本迁移和未结束记录恢复。

### Browser Tests

- 新建 3 人追分并完成犯规、普胜、下一局和结束今日追分。
- 6 人场景中玩家列表可用且主操作保持可见。
- 误点事件可撤销、恢复、编辑和删除。
- 刷新后积分、当前局和顺序完整恢复。
- 历史详情与当前累计积分一致。
- 成绩单能够生成并下载。
- 离线重新打开可以进入应用并继续已保存记录。

### Visual QA

- 390×844、430×932、768×1024、1440×900 四组视口。
- 主计分页无横向滚动、文字遮挡和按钮重叠。
- 2、3、6 人布局均保持稳定。
- 长姓名、四位数和负分不撑破玩家行。
- 浏览器地址栏高度变化时 `100dvh` 布局不裁掉底部操作区。
- 结果面板、设置页和历史页与主计分台保持一致视觉语言。

## 17. Acceptance Criteria

- 新用户可以在 60 秒内完成 3 人默认规则开局。
- 选中玩家后最多两次点击即可记录常见事件。
- 犯规发生后立即更新相关玩家积分，不需要等待本局结束。
- 所有联动结算均可在事件流水中追溯到玩家和规则。
- 撤销、修改和删除不会导致累计积分与流水不一致。
- 每局结束后积分继续累计，规则快照保持不变。
- 下一局顺序建议可确认或手动纠正。
- 刷新或误关页面后可以继续未结束的今日追分。
