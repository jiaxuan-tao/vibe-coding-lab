# Web 交付风险评审 Skill 设计说明

## 目标

将现有 Web 应用验收 Skill 重构为面向轻量 Web 项目的发布决策工具。它不只罗列检查结果，而是将关键用户路径、已取得证据、未覆盖范围和问题影响转换成“可发布、有条件发布或不建议发布”的明确建议。

## 用户问题

独立完成项目时，发布前常见困难不是不知道如何运行构建命令，而是无法判断：哪些流程必须验证、一个发现的问题是否阻塞、缺少真实环境时能否发布，以及应先修复什么。简单的检查清单无法提供这些取舍。

## 决策模型

1. 先定义本次发布的关键用户路径和验收范围。
2. 为每条路径收集构建、静态检查或浏览器操作证据。
3. 将问题分为阻塞、高、中、低四级；级别由用户可达性、核心任务影响、是否有可行绕过方式和证据确定性共同决定。
4. 以阻塞问题、关键路径覆盖和剩余风险为依据，输出发布建议：可发布、有条件发布或不建议发布。

没有证据的事项只能标记为未覆盖，不能以“没有发现问题”替代通过结论。

## Skill 变更

- 名称保持 `web-app-acceptance`，避免破坏已安装用户；显示标题和 README 使用“Web 交付风险评审”。
- 新增“范围与关键路径”“风险分级”“发布建议”三个阶段，并将构建、静态与浏览器检查定位为证据采集。
- 提供固定发布决策单模板：范围、关键路径、证据、风险、未覆盖项、建议与下一步。
- 保留现有脚本的只读和零依赖边界；不引入分数模型或伪精确的风险计算。

## README 变更

README 采用仓库既有作品的叙事顺序：产品预览式摘要、解决的问题、决策模型、使用方式、风险等级、输出示例、核心能力、技术与项目结构、边界、AI 协作与验证、参考与许可。

产品贡献应准确描述为：本项目重新定义的发布决策流程、风险分级口径、降级规则、报告结构、中文交付文案、静态证据脚本和测试。上游来源保留在末尾“参考与许可”，说明其提供浏览器验收方法参考，不将其描述为本项目的主要价值。

## 验证

- 结构测试验证 Skill 包含范围、风险分级和发布建议章节，并按正确顺序输出。
- 结构测试验证 README 包含问题、决策模型、风险等级、示例、边界和归属章节。
- 保留现有两个脚本的单元测试、脚本语法检查和帮助命令验证。
- 检查 README 本地链接和根索引链接。

## 非目标

- 不把风险分级伪装成安全审计、合规认证或用户研究结果。
- 不自动修复目标项目、不绕过登录或支付流程，也不对未实际执行的路径作出通过结论。
- 不隐瞒上游来源或暗示 Anthropic 对本项目的背书。
