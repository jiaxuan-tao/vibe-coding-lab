# Codex 任务交接 Skill 设计说明

## 1. 背景与目标

长任务经常因为切换 Codex 任务、上下文过长、隔日继续或更换设备而中断。普通对话总结会复述过程，却容易漏掉未完成事项、真实文件状态和验证证据，导致下一任务重新检查甚至误判完成度。

本项目要提供一个面向 Codex 的任务交接 Skill，把当前工作整理为可以直接交给下一任务继续的“交接包”。交接包必须区分事实与推断，关联文件和验证证据，并给出准确的下一步，而不是生成泛泛的聊天摘要。

成功标准：

- 用户提出“交接任务”“换个任务继续”“明天接着做”“整理当前进度”等请求时能够正确触发；
- 默认在对话中返回完整交接包，不自动写文件；
- 用户明确要求保存时，才将 Markdown 写到指定路径；
- 自动采集 Git 分支、提交和工作树状态，不修改仓库；
- 已完成事项必须有文件、提交或验证证据，无法证实的内容降级为“待确认”；
- 下一任务能够只阅读交接包就知道目标、当前状态、未完成工作和第一步操作；
- 疑似凭证和个人敏感信息不会原样进入交接包；
- 不依赖账号、后端、付费服务或第三方 Python 包。

上游实现面向 Claude Code，包含首次配置、全局保存目录、SessionStart/SessionEnd Hook、清理脚本、技能推荐器和多份参考材料。其优势是完整的会话生命周期，代价是结构较重，且部分机制不是 Codex 原生能力。

本项目采用“聚焦式重实现”：保留“压缩上下文、引用现有产物、不复制大段内容、交接前去敏”的产品思想，重新设计为适合 Codex 的轻量交接协议。不会复制上游 SKILL 文本、脚本或示例；来源、许可证与差异在 `UPSTREAM.md` 中明确记录。

## 3. 方案选择

### 方案 A：纯提示词模板

只提供 `SKILL.md` 和交接模板。实现最轻，但 Agent 仍可能漏读 Git 状态、把未验证内容写成已完成，交接质量依赖当次模型表现。

### 方案 B：证据辅助交接（采用）

由 Agent 理解对话并写交接包，确定性脚本负责采集工作区证据和校验交接结果。它能保留 Agent 对上下文的理解能力，同时把文件、Git 和结构完整性变成可测试约束。

### 方案 C：自动配置与会话 Hook

复现上游的全局配置、自动载入和会话结束提醒。自动化程度更高，但依赖宿主生命周期，容易产生后台行为和目录污染，不适合作为首版 Codex Skill。

## 4. 产品边界

### 首版包含

- 当前对话或当前任务的交接总结；
- Git 工作区只读证据采集；
- 固定交接结构和继续工作指令；
- Markdown 交接包校验；
- 明确要求时保存文件；
- 密钥、Token、密码和常见个人信息的疑似泄露检查；
- Git 与非 Git 目录的保守降级；
- 中文输出和 Codex 触发描述。

### 首版不包含

- 自动创建或切换 Codex 任务；
- SessionStart、SessionEnd Hook 或后台监控；
- 全局配置文件和保留期限管理；
- 自动运行测试、构建、提交或推送；
- 自动读取仓库外的个人目录；
- 把交接包当作可信指令直接执行；
- 长期知识库、交接历史检索或多人协作平台。

## 5. 核心流程

1. 判断用户是明确要求交接，还是仅表达“稍后继续”。明确请求直接执行；隐含意图先询问是否需要交接。
2. 确认交接范围为当前任务，并从用户补充或当前未完成主线推断下一任务目标。
3. 在当前工作目录运行只读证据采集脚本，获得 Git 根目录、分支、HEAD、最近提交和工作树文件状态。
4. 逐个回顾本任务主题，将内容归入已完成、未完成、待确认或不进入交接；不得只按时间顺序复述聊天。
5. 生成固定结构的 Markdown 交接包，并把工作区证据与对话事实合并。
6. 运行校验脚本；结构缺失、证据不足、出现占位符或疑似敏感信息时，先修正再输出。
7. 默认把交接包直接返回给用户。只有用户明确要求保存时，才写入用户指定的 Markdown 路径。

计划、采集和校验均为只读操作。保存交接文件是唯一写操作，且必须由用户明确提出路径或保存意图。

## 6. 交接包协议

交接包使用以下顺序，标题不可省略：

1. `## 下一任务目标`
   - 一至两句话说明下一任务要完成什么，以及何时算完成。
2. `## 已完成`
   - 每项使用“结果 — 证据”格式；证据可以是文件、提交、测试命令或外部链接。
3. `## 未完成与下一步`
   - 按执行顺序列出未完成事项；第一项必须能直接开始，不使用“继续完善”等模糊措辞。
4. `## 决策、约束与待确认`
   - 记录已经确定的产品或技术约束、仍未决定的问题、阻塞条件和需要用户授权的动作。
5. `## 文件与工作区状态`
   - 列出仓库、分支、HEAD，以及修改、暂存、未跟踪和本任务关键文件；不粘贴完整 diff。
6. `## 验证结果`
   - 每条包含命令或检查方式、结果和时间；没有运行的验证明确写“未运行”，不能推断通过。
7. `## 风险与恢复提示`
   - 说明未提交改动、部分完成、凭证需求、外部状态和可能需要回滚的事项；没有则写“未发现已知风险”。
8. `## 新任务启动指令`
   - 给出一段可直接复制到新 Codex 任务的指令，包含目标、工作目录、必读文件、第一步和禁止事项。

不要求每节篇幅相同。空状态应明确写“无”或“未运行”，不能删除标题，也不能编造内容填充。

## 7. 证据模型

### 已完成

一项工作只有满足以下任一条件，才能放入“已完成”：

- 存在明确的文件或可定位内容；
- 存在提交、PR、Issue 或发布链接；
- 存在本任务实际运行过的验证命令及结果；
- 用户在当前任务中明确确认了非代码成果。

只有聊天中的计划、意图或 Agent 自述时，应归入“未完成”或“待确认”。

### 验证

验证状态限定为：

- `通过`：当前任务中真实执行且退出成功；
- `失败`：真实执行且失败；
- `部分通过`：只有部分检查完成；
- `未运行`：没有本任务证据；
- `结果未知`：运行过但输出不完整或无法确认退出状态。

不得把旧任务、README 描述或推测当作当前验证结果。

### 工作区

脚本只读取当前路径及其 Git 元数据，使用 `git status --porcelain=v1 -z` 避免文件名解析歧义。非 Git 目录返回 `is_git_repository: false` 和明确说明，不扫描上级目录以外的个人文件。

## 8. 组件设计

### `SKILL.md`

定义触发条件、隐含交接意图的确认门槛、证据分类、交接步骤、保存边界和失败报告。正文保持简洁，详细协议放入参考文件。

### `references/handoff-contract.md`

记录八节交接协议、字段要求、证据规则、验证状态和一份完整示例。Agent 在生成交接包前必须读取。

### `scripts/inspect_workspace.py`

只读采集当前工作区并输出 JSON：

- 输入：可选目录、最近提交数量；
- 输出：扫描时间、请求目录、Git 根目录、分支、HEAD、最近提交、工作树条目和错误；
- 不执行构建、测试、网络请求或写操作；
- Git 不可用、目录不存在、命令超时或输出无法解析时返回机器可读错误与非零退出码。

### `scripts/validate_handoff.py`

校验 Markdown 交接包：

- 八个标题齐全且顺序正确；
- 不包含 `TODO`、`TBD`、`待补充` 等占位文本；
- “已完成”条目包含证据分隔符或可识别证据；
- “验证结果”明确出现五种限定状态之一；
- “新任务启动指令”包含工作目录、第一步和禁止事项；
- 检出常见密钥、Bearer Token、私钥、密码赋值、邮箱和中国大陆手机号模式；
- 默认严格模式发现错误即退出 1，`--json` 输出机器可读报告。

脚本只做保守检查，不声称能识别所有敏感信息；Agent 仍需人工语义复核。

### `README.md`

面向用户解释问题、工作流、安装、使用示例、输出协议、产品设计、边界、测试、上游来源和许可。叙事重点是连续工作体验与证据可信度，而不是中文化或复刻过程。

## 9. 错误与隐私处理

- 当前目录不存在：停止生成证据，向用户报告路径问题；
- 非 Git 目录：继续生成交接包，但明确工作区证据受限；
- Git 命令失败：保留错误信息，不猜测分支和文件状态；
- 工作树为空：明确写“工作树干净”，不省略文件状态；
- 验证没有证据：标记“未运行”，不补写可能通过；
- 交接内容含疑似敏感信息：默认阻止输出原文，使用 `[REDACTED]` 后重新校验；
- 用户要求保存但未给路径：先返回对话版本，再询问保存位置，不自行写入仓库；
- 交接文件目标已存在：拒绝覆盖，除非用户明确要求更新该文件；
- 外部链接、远端提交或部署状态无法核验：标记“待确认”，不把本地状态等同于发布状态。

## 11. 测试策略

### Skill 行为评估

- 无 Skill 基线：让新 Agent 为一个含未提交文件、失败测试和未决策事项的任务生成交接，记录其遗漏和无证据宣称；
- 触发评估：覆盖“交接给下个任务”“明天继续”“总结一下进度”及“写周报”“普通项目总结”等邻近请求；
- 前向评估：使用临时 Git 仓库和模拟任务上下文，确认输出完整、证据可追踪、未运行验证不被写成通过。

### 自动测试

- Git 与非 Git 目录采集；
- 修改、暂存、未跟踪、重命名和含特殊字符文件名；
- 缺失目录、Git 命令错误与稳定 JSON 输出；
- 完整交接包通过；
- 缺失标题、标题错序、占位符、无证据完成项、模糊验证状态失败；
- 密钥、Token、私钥、邮箱和手机号检测；
- README 本地链接、安装命令、来源与许可证；
- 根 README、项目索引更新且展示页保持不变；
- 其他已发布 Skill 的回归测试。

## 12. 发布标准

- Skill 专属测试全部通过；
- 官方 Skill 结构校验或等价检查通过；
- 前向评估没有丢失阻塞、文件状态和验证边界；
- README 准确说明产品价值、Codex 使用方式和能力边界；
- `UPSTREAM.md` 与许可证满足 MIT 归属要求；
- 独立代码复审没有 Critical 或 Important 问题；
- 提交范围不包含用户已有的 `AGENTS.md` 和 `docs/SKILLS_WORKFLOW.md` 改动；
- 推送后 GitHub 目录、README 和提交链接可以访问。
