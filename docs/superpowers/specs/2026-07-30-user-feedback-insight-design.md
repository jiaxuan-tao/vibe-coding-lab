# 用户反馈洞察 Skill 设计说明

## 目标

构建 `user-feedback-insight` Codex Skill，把访谈记录、客服工单、问卷开放题、应用商店评论等非结构化反馈，整理为可追溯的产品问题、矛盾与机会判断。

Skill 的核心不是情感分类，也不是把每条反馈直接改写成需求，而是让结论始终能够回到原始证据，并明确区分：

- 一条反馈与一个独立用户；
- 样本内出现次数与总体发生率；
- 问题严重度、来源多样性与战略匹配；
- 用户表达的方案与需要验证的产品机会。

## 已确认的产品边界

- 支持本地 UTF-8 Markdown、TXT、CSV 和 JSON 输入。
- 默认只读，不修改原始反馈文件。
- 不依赖数据库、远程模型 API、付费服务或额外 Python 包。
- 不自动生成 PRD，也不替用户决定最终路线图。
- 不因单条意见或同一用户的重复反馈制造虚假多数。
- 不输出无法由样本支持的总体比例、市场结论或因果判断。
- 不将 Skill 添加到 Vibe Coding Lab 产品展示页，只更新仓库 README 的 Skill 索引。

## 方案选择

采用“证据优先的产品机会分析”，不采用以下两种方案：

1. 纯情感与标签统计：实现简单，但只能提供描述性报表，不能支持产品判断。
2. 直接生成需求池：输出看似完整，但容易把用户提出的功能当成已验证需求。

推荐方案先建立证据台账，再形成主题与机会判断。功能建议只能作为待验证响应，不直接等同于机会。

## Skill 工作流

1. 明确分析问题、样本来源、时间范围和已知偏差。
2. 对本地文件运行只读预处理脚本，生成稳定反馈 ID、识别可能重复项、统计独立来源并提示直接身份信息。
3. 将复合反馈拆成原子证据，记录场景、问题、影响、现有替代方式、用户方案与不确定性。
4. 聚类主题，同时保留矛盾意见、异常样本和无法归类项。
5. 分别判断样本内频次、严重度、来源多样性、证据质量与战略匹配，不合成伪精确总分。
6. 将主题转写为产品机会：目标用户、场景、待解决问题、证据、反证、风险和最小验证动作。
7. 给出 `立即处理`、`进入验证`、`持续观察` 或 `暂不推进` 四种行动建议之一。
8. 仅在用户明确要求时，将已确认机会继续整理为 PRD 输入或路线图候选。

## 确定性脚本

提供 `scripts/prepare_feedback.py`：

- 接受 `.md`、`.txt`、`.csv` 和 `.json`；
- 将输入规范化为统一 JSON 记录；
- 为每条记录生成稳定的 `FB-0001` 格式 ID；
- 检测完全重复与规范化文本重复；
- 在存在来源字段时统计独立来源；
- 检测邮箱和中国大陆手机号形式的潜在直接身份信息；
- 保留源文件与原始行号或记录序号；
- 仅输出到标准输出，不写回源文件。

脚本不负责语义聚类、情感判断、产品优先级或匿名化替换，避免把机械检测伪装成产品洞察。

## 输出契约

标准输出按以下顺序组织：

1. `分析范围与限制`
2. `证据台账`
3. `主题与矛盾`
4. `产品机会`
5. `行动建议`
6. `待补证据`

每个产品机会必须包含：

- 机会陈述；
- 相关证据 ID；
- 反证或矛盾；
- 样本内频次与独立来源数；
- 严重度；
- 证据置信度；
- 最小验证动作；
- 行动建议。

## 基线测试观察

三组无 Skill 测试表明，通用产品分析能够识别主要问题和部分样本偏差，但仍有以下缺口：

- 输出缺少统一证据台账，结论难以稳定回溯；
- 同一用户两次反馈会被描述为“证据较强”，独立来源不足没有成为约束；
- 容易直接给出 P0/P1 和路线图，没有先区分问题机会与功能方案；
- 频次、严重度、证据质量和战略匹配常被混合成一个优先级判断。

Skill 必须通过结构化输出契约解决这些形状问题，而不是只增加禁止性提醒。

## 测试策略

- 单元测试覆盖四种输入格式、稳定 ID、重复检测、来源统计、PII 提醒、空输入、非 UTF-8 和只读行为。
- 静态契约测试覆盖 frontmatter、触发边界、输出结构、来源与许可证文档。
- 仓库集成测试确认 README 索引存在，展示页未添加 Skill 卡片。
- 行为测试复用三组基线场景，检查证据 ID、独立来源、矛盾保留、样本限制和机会优先于功能的输出行为。
