# PRD 需求决策评审 Skill 设计说明

## 目标

创建一个面向 Codex 的中文 PRD 需求决策评审 Skill。它以评审为主、修订为辅，帮助个人开发者和产品人员在进入设计或开发前判断：用户问题是否成立、范围是否合适、完成标准是否可验证，以及当前需求是否值得继续推进。

Skill 不以章节数量或表面完整度给 PRD 打分，也不把 AI 推测补写成事实。它将已有证据、明确需求、合理假设和待确认事项分开，并给出“可进入设计、有条件进入或暂不建议推进”的唯一结论。

## 用户问题

使用 AI 编写 PRD 时，常见问题并不是缺少模板，而是文档看起来完整，却仍可能存在以下风险：

- 直接从解决方案出发，没有说明目标用户和真实问题；
- 把未经验证的判断写成用户事实；
- MVP 范围不断扩张，核心价值无法独立交付；
- 成功指标与需求目标没有对应关系；
- 用户流程、异常状态或能力边界缺失；
- 验收标准不可观察，无法判断是否完成；
- AI 只负责补全文档，没有对需求是否应继续推进作出判断。

## 方案选择

不采用以下两种方案：

1. **完整度清单**：只能判断章节是否存在，无法判断需求方向与内容质量。
2. **量化评分**：会把不同性质的产品判断压缩成缺少依据的总分，制造虚假精确。

采用**证据驱动的需求决策门**。自动检查只负责提供结构证据，最终结论必须综合用户问题、需求证据、范围、流程、成功条件和未解决假设。

## 使用模式

### 评审模式

当输入是已有 PRD、产品说明或仓库文档时：

1. 读取现有材料并识别本次需求目标。
2. 按评审模型检查关键内容和内部一致性。
3. 输出结论、关键缺口、事实与假设、最小补充动作。
4. 不直接重写原文，除非用户明确要求修订。

### 想法梳理模式

当输入只有一句产品想法或功能描述时：

1. 先整理为轻量产品 Brief，而不是假装生成完整 PRD。
2. 将缺少证据的内容标记为假设。
3. 只提出会改变产品方向的少量问题。
4. 判断它是否已经具备进入详细设计的条件。

### 修订模式

仅在用户要求改写或补全时，根据评审结论生成修订版。修订必须保留事实、假设和待确认项的区别，不得为了文档完整而虚构用户研究、数据或业务约束。

## 评审模型

按以下顺序评审，使前置方向问题能够尽早终止无效的细节补全：

1. **用户问题**：目标用户、发生场景、当前障碍和问题影响是否明确。
2. **证据与假设**：哪些来自用户材料、数据或观察，哪些只是合理推断，哪些尚未确认。
3. **目标与指标**：产品目标是否与用户问题对应，成功标准是否可观察、可验证。
4. **MVP 范围**：核心价值能否独立交付，包含项、排除项和后续项是否清楚。
5. **关键流程**：主路径、关键状态、异常路径和用户可见结果是否完整。
6. **需求与验收**：每项要求是否描述一个可观察行为，验收场景是否真正验证要求。
7. **依赖与风险**：外部服务、数据、权限、合规、技术前提和不可逆影响是否被说明。
8. **一致性**：问题、目标、范围、流程、指标和验收之间是否相互支持，是否存在范围漂移或矛盾。

## 结论规则

- **可进入设计**：用户问题、目标、核心范围和关键流程明确；主要需求可验证；剩余缺口不影响产品方向。
- **有条件进入**：核心方向基本成立，但仍有会影响范围、指标或关键流程的假设。可以继续原型或探索，不应把未确认内容直接交给完整开发。
- **暂不建议推进**：目标用户或问题不清、证据与假设混淆、范围无法收敛、成功条件无法定义，或关键依赖使当前方案不可行。

不输出总分。关键发现按处理方式分为：

- **阻塞项**：未解决前不应进入设计或开发；
- **需确认**：可以继续有限探索，但必须标明假设和影响；
- **可优化**：不影响当前方向，可在后续修订。

## 技术与文件设计

项目目录使用 `prd-decision-review-skill/`，包含：

- `SKILL.md`：触发条件、评审顺序、结论规则、边界和输出契约；
- `agents/openai.yaml`：Codex 中的显示名称、简短说明和默认提示词；
- `references/prd-review-framework.md`：详细评审口径、正反例和常见缺口；
- `scripts/inspect_prd.py`：只读检查 Markdown 标题、占位符、模糊表述、成功指标和验收场景等结构证据；
- `tests/`：脚本、文档结构、触发行为和典型任务验证；
- `README.md`：面向使用者说明产品问题、决策模型、使用方式、示例、边界、产品设计贡献和来源；
- `UPSTREAM.md`、`LICENSE.txt`：记录参考来源和 MIT 许可。

脚本使用 Python 标准库，不安装依赖、不修改被检查文件，也不根据结构检查自动计算产品分数。

## 上游与复现策略

参考 GitHub Spec Kit 的用户场景、独立测试、可衡量结果和假设表达，以及 OpenSpec 的意图、范围、可观察要求、场景验证和评审顺序。

采用**参考思想并轻量重实现**的策略：

- 不复制或安装两者的 CLI、完整目录规范和工程工作流；
- 不把工程规格管理包装成原创产品方法；
- 将适用于产品需求判断的部分重新组织为中文 Codex Skill；
- 在 `UPSTREAM.md` 和 README 中保留仓库、许可证、参考内容和差异说明；
- 项目使用 MIT 许可证，与两个上游来源保持兼容。

## 验证设计

### 基线失败场景

先在没有 Skill 的条件下验证三类任务：

1. 面对模糊想法，Agent 是否直接生成看似完整的 PRD 并虚构用户事实。
2. 面对缺少成功指标和验收标准的 PRD，Agent 是否只补全文案而不给推进结论。
3. 面对结构完整但用户价值和范围矛盾的需求，Agent 是否只评价文档完整度。

### Skill 验证场景

加入 Skill 后，验证它能够：

- 区分事实、假设和待确认项；
- 先检查用户问题与范围，再检查文档细节；
- 给出唯一、可解释的推进结论；
- 将缺口转成最小下一步，而不是泛化建议；
- 在未被要求时不重写 PRD；
- 在修订时不虚构用户研究、数据或业务约束；
- 对结构完整但方向错误的需求给出否定或条件性判断。

脚本测试覆盖正常 PRD、缺失章节、占位符、无验收场景、非 Markdown 输入和只读行为。仓库级检查覆盖 frontmatter、README 本地链接、安装命令、许可证和根索引。

## README 叙事重点

README 与仓库其他作品保持一致，但重点体现以下产品能力：

- 将“写一份 PRD”重新定义为“判断一个需求是否值得进入下一阶段”；
- 建立用户问题、证据、目标、范围、流程、指标和验收之间的决策链；
- 对 AI 容易制造的完整感、假设污染和范围扩张设置明确边界；
- 用结论、影响、依据和最小动作表达产品取舍。

来源与许可放在末尾准确说明，不使用“完全原创”或弱化必要归属，也不把项目主体叙事写成对上游项目的简单中文化。

## 非目标

- 不替代用户研究、数据分析、商业评估或正式需求评审会议；
- 不根据章节数量计算 PRD 质量分；
- 不自动修改用户文件，除非用户明确要求生成修订版；
- 不生成技术架构、实施任务或代码；
- 不把未经验证的市场、用户或业务判断写成事实；
- 不保证通过评审的需求一定取得商业成功。
