# Web 交付风险评审 Skill

一个面向 Codex 的中文发布决策工具，用于回答轻量 Web 项目在上线前最关键的问题：**现在能不能发？如果不能，最小需要先解决什么？**

它不把验收简化为“测试通过 / 测试失败”。它先定义用户必须完成的关键任务，再收集构建、静态检查与浏览器操作证据，最后把发现的问题和未覆盖范围转化为可发布、有条件发布或不建议发布的明确建议。

## 🎯 它解决什么问题

独立完成 Web 项目时，发布前真正难的通常不是“会不会运行 `npm run build`”，而是判断：

- 这次发布最重要的用户任务是什么，哪些路径必须验证？
- 一个报错、失效链接或移动端问题，到底是阻塞发布，还是可以记录到下一轮？
- 没有生产账户、真实数据或第三方服务时，剩余的不确定性能否接受？
- 如果只能优先修一个问题，哪个问题最影响用户完成任务？

常见检查清单会列出很多动作，却无法解释检查结果和发布结论之间的关系。这个 Skill 将验收改造成一套发布判断：以关键路径为范围，以实际证据为依据，以风险分级表达取舍。

## 🧭 决策模型

整个流程由四层组成：

1. **定义关键路径**：明确发布目标、目标用户和用户必须完成的 1 至 3 条任务。
2. **采集证据**：使用已有构建与测试命令、只读静态检查和浏览器操作验证路径。
3. **评审风险**：按用户影响、任务影响、是否可绕过、证据是否充分分为阻塞、高、中、低四级。
4. **给出建议**：结合关键路径覆盖、风险和未覆盖范围，输出可发布、有条件发布或不建议发布。

这不是风险打分器。它不把不确定性压缩成看似精确的分数，而是要求每个判断可解释、可复验、可讨论。

## 🧭 使用方法

在 Codex 中提出：

- `评审这个 Web 项目是否可以发布`
- `检查这次改动的关键用户路径，并给发布建议`
- `这个页面的问题会不会阻塞上线？`
- `发布前做一次构建、交互和风险验收`

Skill 会先确认本次发布目标和关键路径，再按项目实际环境选择证据采集方式。对于已有 `package.json` 的项目，会读取脚本而非猜测框架；对于静态站点，会检查可确定的本地链接和资源；对于关键交互，会用浏览器辅助验证实际页面。

## 📊 风险等级

| 等级 | 对用户与发布的含义 | 默认处理 |
| --- | --- | --- |
| **阻塞** | 用户无法进入产品，或核心任务无法完成、结果明显错误、隐私或安全风险不可接受 | 不建议发布，修复后复验 |
| **高** | 重要路径对部分用户不可用，且没有清晰绕过方式 | 默认不发布；仅在缩小范围或关闭受影响能力后考虑有条件发布 |
| **中** | 非核心体验受影响、存在临时绕过方式，或证据尚不足以确认影响范围 | 可以有条件发布，并明确后续修复动作 |
| **低** | 不影响任务完成的轻微体验、文案或视觉问题 | 可以发布，进入后续迭代 |

没有实际执行的检查不是“通过”，也不自动是缺陷；它必须作为未覆盖范围被说明，并参与发布判断。

## ✨ 核心能力

- 从“要发布什么”开始定义验收范围，而不是机械运行通用检查。
- 将每条关键用户路径写成可观察、可复现的操作与结果。
- 读取项目已有构建、测试和包管理配置，避免猜测命令或改变依赖。
- 提供零依赖、只读的静态链接与资源检查，为交付判断补充确定性证据。
- 区分事实、风险判断、未覆盖范围和发布建议，避免模糊结论。
- 用阻塞、高、中、低四级风险帮助决定先修什么，而非按问题数量排序。
- 对无法验证的登录、支付、第三方服务和生产数据路径明确降级，不虚构通过结果。

## 🛠️ 本地运行

Skill 可直接安装到 Codex，也可以在仓库中运行脚本与测试。

```bash
git clone https://github.com/jiaxuan-tao/vibe-coding-lab.git
cd vibe-coding-lab/web-app-acceptance-skill
python3 -m unittest discover -s tests -v
```

检查一个项目的可用验收信息：

```bash
python3 scripts/inspect_web_project.py /path/to/project
```

检查已生成的静态站点：

```bash
python3 scripts/check_static_site.py /path/to/project/dist
```

第二个命令发现缺失本地页面或资源时返回退出码 1，适合接入已有 CI；它不会验证动态路由、外链、登录态或业务逻辑。

若只安装 `SKILL.md`：

```bash
mkdir -p ~/.codex/skills/web-app-acceptance
curl -sL https://raw.githubusercontent.com/jiaxuan-tao/vibe-coding-lab/main/web-app-acceptance-skill/SKILL.md \
  > ~/.codex/skills/web-app-acceptance/SKILL.md
```

如需使用脚本、清单和许可证，请复制完整目录。

## 🧱 技术实现

- **流程层**：`SKILL.md` 定义范围、证据、风险与发布建议的顺序。
- **项目检测**：Python 标准库读取 `package.json`、锁文件和已有脚本，识别候选构建目录与配置警告。
- **静态证据**：Python `HTMLParser` 检查静态 HTML 的本地页面链接与资源引用，并显式报告跳过项。
- **浏览器验收**：根据项目页面实际状态验证关键路径，而不是预先猜测选择器。
- **自动测试**：Python `unittest` 覆盖脚本正常、缺失配置、无效 JSON、缺页、缺资源、文档结构和根索引。

项目不要求后端、账号系统、数据库、浏览器自动化依赖或远程分析服务。

## ⚠️ 能力边界

- 它是发布风险评审工具，不是安全审计、合规认证、性能压测或完整端到端测试平台。
- 风险等级是基于当前范围和实际证据的交付判断，不替代用户研究、数据分析或生产监控。
- 没有凭证、真实数据或可用服务时，不会绕过登录、支付或第三方权限来制造验证结果。
- 静态检查只能发现可确定的本地引用问题，不能证明动态路由、外部资源或业务规则正确。
- 它提供发布建议，不替项目负责人承担最终发布决策。

## 🤖 AI 辅助开发说明

本项目通过 Vibe Coding 方式迭代。作者负责定义“什么是本次发布的关键用户任务”、风险分级口径、可接受的降级条件、输出结构和最终验收标准；Codex 用于协助实现脚本、测试、文档整理与验证。

产品能力不在于让 AI 多跑几个命令，而在于将发布前模糊的焦虑转为可讨论的决策：什么证据足够、什么风险不能接受、什么可以带着条件发布。所有“通过”都应有可复现证据，所有未验证内容都必须留在风险账本中。
