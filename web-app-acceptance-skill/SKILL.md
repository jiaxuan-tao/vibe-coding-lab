# Web 应用验收

将验收范围限定在用户指定的项目路径；未指定时先说明将检查当前工作目录。脚本只读、不安装依赖、不修改项目文件，也不上传数据。

## 输出原则

- 每个结论都附上实际执行的命令、结果和范围。
- 将“通过”“失败”“跳过”和“未覆盖风险”明确分开。
- 只把已验证的事项写为通过；动态路由、登录态、第三方资源和业务规则不因静态检查通过而视为已验收。

## 1. 项目检测

先运行项目检测，了解包管理器、可用脚本和候选构建目录：

```bash
python3 scripts/inspect_web_project.py <项目目录>
```

- 若没有 `package.json` 或没有 `build` 脚本，记录警告并询问或从项目文档确认正确命令。
- 不自行执行 `install`、不猜测框架、不将检测结果当作构建成功。

## 2. 构建验证

仅在依赖已经安装、且检测到明确构建脚本时，使用项目已有包管理器执行构建，例如：

```bash
npm run build
```

- 记录完整退出结果；构建失败时先报告失败位置，不继续宣称交付可用。
- 不因执行验收而升级依赖、改写锁文件或修复业务代码；只有用户要求修复时才进入开发工作。

## 3. 静态检查

对已存在的静态输出目录运行检查：

```bash
python3 scripts/check_static_site.py <静态目录>
```

它检查 HTML 中可确定的本地页面链接与静态资源引用。外链、锚点、动态路由以及越出站点目录的引用会被列为跳过项或警告，不会被误判为通过。

## 4. 浏览器辅助验收

读取 [浏览器验收清单](references/browser-acceptance-checklist.md)，并使用当前可用的浏览器控制能力完成与项目相关的检查：

1. 打开首页并等待页面稳定，记录控制台错误和网络失败。
2. 验证用户指定或项目主流程中最重要的 1 至 3 条路径；先观察已渲染界面，再选择稳定的元素定位方式。
3. 检查窄屏与宽屏下是否存在明显溢出、遮挡、不可点击或无法返回的问题。
4. 记录未执行的登录、付费、第三方 API 或需真实数据的流程，并说明原因。

不要在未看到页面渲染状态前猜测选择器；不要把截图存在等同于交互正确。

## 5. 验收结论

按以下结构用中文输出：

```text
Web 应用验收 · YYYY-MM-DD

范围：<项目路径与已执行环境>

通过
- <已验证事项与证据>

失败
- <问题、复现命令或页面路径、影响>

跳过与未覆盖风险
- <未检查事项、原因与后续建议>

结论：通过 / 有条件通过 / 未通过
```

若存在构建失败、关键路径不可用或静态本地引用失效，结论为“未通过”。只有所有已定义关键路径都验证完成且没有阻塞问题时，才能写“通过”。
