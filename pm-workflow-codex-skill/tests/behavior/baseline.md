# 纪念日新增弹窗异常处理优化

## 1. 背景与问题

当前“新增纪念日”弹窗在以下情况下仍会关闭，且用户已填写内容丢失：

- 名称为空
- 日期为空
- 日期非法
- 保存接口失败

这会让用户误以为保存成功，同时增加重复填写成本。

## 2. 目标

修复后的核心规则：

> 只有服务端明确返回保存成功，弹窗才允许自动关闭，并触发纪念日列表刷新。

校验失败或接口失败时：

- 弹窗保持打开
- 已填写的名称、日期及其他表单内容保持不变
- 明确提示失败原因
- 用户可以直接修改或重试

用户主动点击“取消”或关闭按钮的行为沿用现有产品规则，不在本次改动范围内。

## 3. 交互与业务规则

### 3.1 前端校验

用户点击“保存”后，按照以下顺序校验：

1. 名称是否填写
2. 日期是否填写
3. 日期是否合法
4. 校验通过后调用保存接口

名称规则：

- 去除首尾空格后为空，视为未填写
- 非空时，长度及特殊字符限制沿用现有规则
- 若当前没有长度限制，建议最长 50 个字符

日期规则：

- 日期不可为空
- 必须是系统能够解析的完整日期
- 不允许不存在的日期，如 2025-02-30
- 可选日期范围及是否允许未来日期，沿用当前业务规则；若超过范围，显示对应提示

校验失败时：

- 不调用保存接口
- 弹窗不关闭
- 表单内容不清空
- 在对应字段下方显示错误提示
- 焦点定位到第一个错误字段
- 用户修改字段后，清除该字段已有的校验提示；再次保存时重新校验全部字段

建议提示文案：

| 场景 | 提示文案 |
|---|---|
| 名称为空 | 请输入纪念日名称 |
| 日期为空 | 请选择纪念日日期 |
| 日期格式或日期值非法 | 请选择有效日期 |
| 日期超出业务允许范围 | 请选择允许范围内的日期 |

### 3.2 保存请求中

接口请求发出后，弹窗进入“保存中”状态：

- 保存按钮显示“保存中…”或加载状态
- 禁用保存按钮，避免重复提交
- 禁止通过遮罩、Esc、关闭按钮或取消按钮关闭弹窗，避免出现请求结果不明确或重复保存
- 保留所有表单内容

请求结束后恢复按钮和关闭能力。

### 3.3 保存成功

仅当接口返回明确的业务成功结果时：

1. 关闭弹窗
2. 清空本次弹窗表单状态
3. 刷新纪念日列表
4. 显示“保存成功”提示

列表刷新建议使用接口返回的新纪念日数据先更新本地列表，再执行一次服务端列表刷新，以减少保存成功后列表短暂缺少新数据的情况。

若保存成功但后续列表刷新失败：

- 不回退已经成功的保存
- 提示“保存成功，列表刷新失败，请重试”
- 保留或插入接口返回的新纪念日数据
- 提供现有页面刷新机制，或在下一次进入页面时重新拉取

### 3.4 保存失败

以下情况均按保存失败处理：

- 网络中断或请求超时
- HTTP 请求失败
- 接口返回业务失败
- 返回数据无法确认是否保存成功

处理方式：

- 弹窗保持打开
- 所有输入内容保持不变
- 保存按钮恢复可点击
- 不刷新纪念日列表
- 展示用户可理解的错误提示
- 用户可直接点击“保存”重试

建议提示文案：

| 场景 | 提示文案 |
|---|---|
| 网络异常或超时 | 网络异常，请检查网络后重试 |
| 服务异常 | 保存失败，请稍后重试 |
| 服务端返回明确原因 | 优先展示经过产品映射的业务提示 |
| 名称重复等业务冲突 | 按服务端错误码展示具体提示 |

不要直接展示堆栈、HTTP 状态码或未经处理的服务端错误文本。

## 4. 状态逻辑

| 当前状态 | 用户操作或结果 | 弹窗 | 表单内容 | 列表刷新 |
|---|---|---|---|---|
| 编辑中 | 点击保存，校验失败 | 保持打开 | 保留 | 否 |
| 编辑中 | 点击保存，校验通过 | 进入保存中 | 保留 | 否 |
| 保存中 | 接口成功 | 关闭 | 关闭后清空 | 是 |
| 保存中 | 接口失败或超时 | 保持打开 | 保留 | 否 |
| 保存中 | 重复点击保存 | 不重复请求 | 保留 | 否 |
| 编辑中 | 用户主动取消 | 按现有规则关闭 | 按现有规则处理 | 否 |

## 5. 接口与实现约定

前端应以明确的业务成功标识判断保存结果，不能仅凭请求 Promise 结束或收到任意 HTTP 响应就关闭弹窗。

建议接口成功返回至少包含：

- 新增纪念日 ID
- 名称
- 日期
- 服务端最终保存的数据

保存按钮的异步处理应遵循：

```text
点击保存
→ 执行前端校验
→ 校验失败：保留弹窗和输入
→ 校验通过：进入保存中并调用接口
→ 接口成功：关闭弹窗、清空状态、刷新列表
→ 接口失败：退出保存中、保留弹窗和输入、展示错误
```

应避免在通用 `finally`、弹窗确认回调结束或请求发出后直接执行关闭及表单重置；关闭与重置只能位于明确的成功分支。

## 6. 验收标准

1. 名称为空时点击保存：

   - 接口未被调用
   - 弹窗不关闭
   - 日期等其他输入保持不变
   - 名称字段显示“请输入纪念日名称”

2. 日期为空时点击保存：

   - 接口未被调用
   - 弹窗不关闭
   - 名称等其他输入保持不变
   - 日期字段显示“请选择纪念日日期”

3. 输入非法日期时点击保存：

   - 接口未被调用
   - 弹窗不关闭
   - 所有输入保持不变
   - 日期字段显示对应错误

4. 保存接口返回业务失败、HTTP 失败、超时或断网时：

   - 弹窗不关闭
   - 所有输入保持不变
   - 保存按钮恢复可点击
   - 列表不刷新
   - 页面展示错误提示
   - 再次点击保存可以正常重试

5. 接口请求过程中连续点击保存：

   - 只产生一次保存请求
   - 弹窗不能被意外关闭

6. 保存成功时：

   - 弹窗关闭
   - 列表刷新并展示新增纪念日
   - 成功提示只出现一次
   - 再次打开新增弹窗时，表单为空

7. 首次保存失败、随后重试成功时：

   - 失败后输入内容完整保留
   - 重试成功后仅新增一条数据
   - 弹窗关闭且列表展示新增项

## 7. 数据埋点与成功指标

建议记录以下事件：

- 新增弹窗打开
- 点击保存
- 前端校验失败及失败字段
- 保存请求成功
- 保存请求失败及错误类型
- 保存失败后重试
- 重试成功
- 弹窗主动取消

上线后观察 7～14 天，建议成功指标为：

- 校验失败或接口失败导致的弹窗自动关闭率降至 0
- 保存失败后的表单内容保留率达到 100%
- 单次点击产生重复保存请求的比例降至 0
- 保存成功后列表出现新增数据的比例达到 99.9% 以上
- 因前端校验遗漏产生的无效保存请求明显下降
- 保存失败后重试成功率可作为辅助指标持续观察

## 8. 回归范围

除新增纪念日主流程外，需要回归：

- 修改纪念日弹窗是否复用了相同表单或提交逻辑
- Enter 键提交
- 移动端键盘与日期选择器
- 点击遮罩、Esc、关闭按钮和取消按钮
- 弱网、断网、超时及快速重复点击
- 保存成功后的列表排序、空状态切换和重复数据问题
- 不同日期格式、闰年日期及月末日期处理

## 基线检查表

| 检查项 | 观察 | 判定 |
|---|---|---|
| invented metrics | 自行给出“99.9% 以上”“100%”“降至 0”等目标值，没有数据基线或用户确认。 | FAIL |
| missing scope confirmation | 未向用户确认日期范围、名称长度、取消关闭行为、接口成功标识等范围；直接以“沿用现有规则”或建议值补全。 | FAIL |
| Markdown-only output | 输出仅为 Markdown 产品方案。 | FAIL |
| missing HTML prototype | 未创建或提供可交互 HTML 原型。 | FAIL |
| missing failure-state acceptance | 已覆盖空名称、空日期、非法日期、接口失败/超时/断网、重试等失败态验收。 | PASS |
| missing mechanical validation | 未提供可执行测试、验证脚本、命令或其他可复现的机械验证证据。 | FAIL |

RED 结论：六项中有五项失败，满足“至少一项失败”的 RED 基线要求，无需追加时间压力后重跑。
